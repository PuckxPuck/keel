# API conventions

REST over JSON, OpenAPI 3.1 generated by Huma. Base path `/api/v1`.

## Response shape

Every response has one of exactly two shapes, enforced by Go types, so no operation can answer in a format of its own (decision D24).

**Success** (`application/json`): an object with `data`, and `meta` and `links` only where they mean something.

```json
{"data": {"id": "01JB8Q...", "number": "INV-0042", "total": {"amount": 1250, "currency": "USD"}, "version": 3}}
```
```json
{"data": [{...}, {...}],
 "meta": {"limit": 50, "total": null, "totalCapped": false},
 "links": {"next": "<cursor>", "prev": null}}
```

**Error** (`application/problem+json`, RFC 9457): see [Errors](#errors).

- Handlers return `httpx.One[T]`, `httpx.List[T]`, `httpx.Feed[T]`, `httpx.NoContent`, or `httpx.Created[T]` for a create that answers 201 with the new resource or 200 with the one already stored (a client-made id sent again; `httpx.CreatedOf(v, created)`, both statuses documented). Nothing else compiles as an operation output, and the operation walk test checks every registered output schema against the envelope.
- `data` is always an object for a single resource and always an array for a list, never null for a list (empty is `[]`).
- Actions (`/approve`) return the updated resource in `data`. Deletes return 204 with no body.
- Why not JSON:API: it nests fields under `data.attributes` and mixes related records in an untyped `included` array, which generated clients type poorly; it brings its own error format beside RFC 9457; Huma does not support it. This envelope keeps JSON:API's useful part (a predictable top level) without those costs.

## Paths and operations
- Plural nouns, kebab-case: `/api/v1/purchase-orders`, `/api/v1/purchase-orders/{orderId}/lines`.
- Children nest one level under their parent; cross-parent reads get their own root.
- Actions that are not CRUD are POST sub-resources named as verbs: `/purchase-orders/{id}/submit`, `/approve`, `/cancel`.
- Every operation has: a camelCase verb-first `OperationID` (`listPurchaseOrders`, `approvePurchaseOrder`), `Tags`, a `Summary`, documented error statuses, a `Need`, and a rate-limit class.
- `GET` and `HEAD` never change state.

## Shapes
- JSON fields camelCase. Ids are UUID strings. Dates `YYYY-MM-DD`. Instants RFC 3339 in UTC.
- Money is an object `{"amount": 1250, "currency": "USD"}` with `amount` in integer minor units (D18). A response in one currency throughout may give `currency` once at the top level. Rates and percentages are decimal strings (`"7.5"`).
- Input structs per operation, with schema bounds (`maxLength`, `minimum`, `maximum`, `maxItems`, `enum`, `format`). Unknown fields are rejected.
- Editable records return `version`; updates send it back; a stale version is 409 `stale_version` with who changed it and when.
- Records the client edits carry `can: {edit, delete, ...}` so clients never re-derive permissions. `GET /me` returns the user, roles and permission codes.
- Partial updates use `PATCH` with explicit optional fields (pointer or `omitzero`), never "empty means unchanged".

## Lists
Every list is paginated; no operation returns an unbounded array.

**Keyset (default).** Request `limit` (default 50, max 100) and `cursor`; response is the list envelope: `data`, `meta.limit`, `meta.total`, `meta.totalCapped`, `links.next`, `links.prev`.

- The cursor is opaque and HMAC-signed (`APP_SESSION_KEYS`). It carries the sort key, the direction, the last row's sort values and id, and a hash of the filters. A cursor used with a different sort or filters is 400 `cursor_mismatch`; a forged or stale-key cursor is 400 `cursor_invalid` (`paging.Mapper` answers both, so handlers return the error as it is). Clients restart from the first page on either.
- Stable under inserts and deletes: no skipped or repeated rows, unlike offset.
- `links.prev` is set when the operation supports going back; most lists only need `links.next`.
- `meta.total` is null unless the operation offers it. When offered, it is opt-in (`includeTotal=true`) and capped: counting stops at 10,000 and `meta.totalCapped` is true. Exact counts of large tables are not free.

**Offset.** Only where a screen genuinely needs numbered pages: `page` and `limit`; the same envelope with `meta.page`, `meta.pages` and `meta.total`. `page * limit` is capped (default 10,000 rows deep); deeper is 400 `page_too_deep` with a hint to filter.

**Sorting.** `sort=field` or `sort=-field` from the operation's allowlist; the id is always the final tie-break. An unknown sort is 400 `unknown_sort`, never silently replaced.

**Filtering.** Named query parameters; multi-value as repeated parameters; bounds in the schema. Free-text `q` has a minimum length and escaped wildcards. Aggregates above a list (counts, sums) are computed in SQL over all matching rows, never from the page.

**Exports** never page through the API. They run in a job (or a streamed response for small sets) that walks the keyset internally.

## Change feeds (sync)
For clients that keep a local copy (offline apps, integrations): `GET /<things>/changes?since=<token>&limit=` returns the list envelope with change entries: `data: [{"op": "upsert"|"delete", "id", "version", "record"}]`, `links.next` (the token to store) and `meta.hasMore`.

- The token is opaque and signed, like a cursor. An empty `since` starts a full sync.
- Deletes come through as tombstones, so the client can remove its copy.
- A feed must never miss a change that commits late. `updated_at > since` does (a transaction that started earlier can commit after the client read past its timestamp), so feeds use the commit-safe watermark in [database.md](database.md#change-feeds).
- The client applies changes in order and stores `links.next` only after applying the page.

## Errors
Every error, from every layer (validation, auth, rate limit, panic recovery, unknown route, method not allowed), is RFC 9457 problem+json with the same members: `type`, `title`, `status`, `detail`, `code` (stable, snake_case), `requestId`, and extension members as needed. Nothing writes a plain-text or HTML error; the router's not-found and method handlers and the recover middleware all go through `problem`. Submitted values are never echoed.

Field errors are an `errors` array, one entry per failing field:

```json
{"status": 422, "code": "validation_failed", "title": "Unprocessable Entity",
 "errors": [{"location": "body.email", "code": "format", "message": "must be an email address"}]}
```

`location` is `body.<path>`, `query.<name>`, `path.<name>` or `header.<name>`, with array indexes as `body.lines[2].qty`. A client form maps `location` to its field once in a shared helper; nothing else on the client parses errors.

| Status | When | Example codes |
| --- | --- | --- |
| 400 | Malformed request | `invalid_json` |
| 401 | Not signed in, or session expired | `unauthenticated`, `session_expired` |
| 403 | Signed in, not allowed | `forbidden` |
| 404 | Not found, or not visible to this user (same answer) | `not_found` |
| 409 | State conflict | `stale_version`, `illegal_transition`, `locked` |
| 413 | Body too large | `too_large` |
| 422 | Valid shape, fails a rule | `validation_failed` (with `errors[]`), `checks_failed` (with `checks[]`) |
| 429 | Rate limited, with `Retry-After` | `rate_limited` |
| 500 | Bug or dependency failure; detail is generic, request id included | `internal` |
| 503 | Draining or dependency down | `unavailable` |

## Idempotency
- `PUT` and `DELETE` are idempotent by design.
- `POST` that creates something a client might retry within minutes (payments, sends) accepts `Idempotency-Key` (signed-in callers only); the first answer below 500 is stored with the key and replayed for 24 hours, and a request whose outcome was lost answers 409 `idempotency_outcome_unknown` rather than running again ([packages.md](../packages.md#idempotency-core)).
- Offline-first clients that may upload days later use client-generated ids instead: the client makes a UUIDv7 (`clientId`) when the record is created on the device, the table has a permanent unique constraint on it, and a repeat upload returns the stored record (200) rather than creating a second. A race between two uploads is caught on the unique violation and answered the same way. This lives in the module that owns the record, not in the kit's idempotency store, because it must never expire.
- Records edited offline carry `version` and the client's `baseVersion`; a mismatch is 409 with the current record so the client can merge.

## Realms and tenants
- Each realm's operations are mounted on its own hosts (D17). An operation belongs to one realm, and may also be exposed on the `api` realm when marked `httpx.Public(since)` ([../integrations.md](../integrations.md#2-the-api-realm-public-api)).

- With tenancy, the tenant comes from the host or the session, never from a path or body field. Ids in paths are looked up inside the current tenant; another tenant's id is a 404.
- `GET /me/tenants` lists the user's tenants (for a tenant switcher) with each one's state and the default first; `POST /auth/tenant` switches and rotates the session.

## Versioning
- Additive changes (new fields, new operations) stay in `/api/v1`. Clients ignore unknown fields.
- Breaking changes need a new operation or a `/api/v2` path, and the old one stays until clients move. `make check` diffs the spec against the last release tag and flags removals.

## Webhooks out
Standard Webhooks headers, emitted in the causing transaction, delivered by jobs with retries and SSRF protection. Details in [../integrations.md](../integrations.md#3-outbound-webhooks). Event payloads use the same `data` envelope: `{"type": "order.paid", "id": "...", "occurredAt": "...", "data": {...}}`.
