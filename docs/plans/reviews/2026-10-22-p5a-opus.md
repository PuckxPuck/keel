# P5a review (Opus)

Scope: internal/kit/{jobs,mail,webhooks,connections,seal} and the migrations 20261022173122_kit_jobs.sql through 20261022173132_kit_oauth_states.sql on both engines.

## Verdict: fix-then-ship

The job queue core holds up:
- The claim uses SKIP LOCKED with the right order, and the Postgres partial index `jobs_ready` serves it (checked with EXPLAIN).
- Leases run on the wall clock, renew every lease/3, and cancel the handler once the last confirmed lease has passed.
- Every outcome write is fenced by `locked_by` and `status = 'running'`.
- A shutdown requeues and refunds the attempt.
- Backoff uses full jitter.
- Schedules enqueue once per slot, under SKIP LOCKED plus a slot unique key.

Mail never holds a transaction during SMTP. Webhook signing matches Standard Webhooks. The OAuth state is hashed, bound to the user and single use.

Three properties the packages promise do not hold:
- The SSRF dialer can be bypassed.
- Mail's at-most-once guard races on Postgres.
- Connections can lose a rotated refresh token.

I proved all three with `go test -overlay` probes.

## Blockers

1. **internal/kit/webhooks/ssrf.go:36-49 and webhooks.go:187: an IPv6 zone identifier bypasses the SSRF check.** `netip.Prefix.Contains` returns false for any address that has a zone, so `Blocked` returns false for `::1%lo0`, `::1%x`, `fe80::1%eth0` and `fd00::1%x`.
   - `checkURL` accepts `https://[::1%25lo0]:8443/`.
   - `resolve` (ssrf.go:106) and the `Control` re-check (ssrf.go:86-91) both pass the zoned literal.
   - Probe: a listener on `[::1]` was reached through `http://[::1%25lo0]:port/` and `http://[::1%25bogus]:port/` (status 299), while `http://[::1]:port/` was refused.
   - A tenant can therefore reach loopback, link-local and ULA services, which is the attack this dialer exists to stop.

   Fix: in `Blocked`, return true when `addr.Zone() != ""` before any other check (a webhook has no legitimate use for a zone). Also refuse a `%` in `u.Hostname()` in `checkURL`. Add `::1%lo0`, `fe80::1%eth0` and `fd00::1%x` to `TestBlocked`, plus one dial case.

2. **internal/kit/mail/service.go:126-139 and 184-199: the "sending" guard is not exclusive, and its order depends on each host's clock.** There are two separate defects.
   - **Stale row on Postgres.** `latest` locks only the newest row: `ORDER BY created_at DESC LIMIT 1 FOR UPDATE`. Under READ COMMITTED, a second transaction that waited on that lock gets back the same, now stale, row after the first commits. It does not see the new `sending` row. Probe: tx1 reads `queued`, inserts `sending` and holds. tx2 waits on tx1, and after tx1 commits, Postgres returns `queued` to tx2 (MySQL returns `sending`). Both runs then record `sending` and both call `Mailer.Send`. That is a silent duplicate, exactly what the outbox is meant to prevent.
   - **Overlapping runs are reachable.** One way is `queue:cancel` followed by `queue:retry` on a running mail job: the cancelled worker learns of the cancel only at its next renewal, up to lease/3 (40 s by default). Others are clock skew between the reaper's host and the worker's host, or a paused process.
   - **Order by wall clock.** Rows are ordered by `created_at` from the wall clock of whichever host wrote them (service.go:208). Example: host A writes `sending` then `failed` (temporary), and host B, whose clock is behind, writes `sending` and crashes after the send. B's `sending` row then sorts before A's `failed`, so the next run reads `failed` and sends again. The first retry delay is 0 to 5 s with full jitter, so even a small skew is enough.
   - **Fix.** Add `seq integer not null` with `unique (message_id, seq)`. Insert `seq = last + 1` and read the latest by `seq`. A concurrent second `sending` insert then fails with a unique violation; treat that as uncertain and stop. The P5a migrations have not shipped, so amend 20261022173125 on both engines. Alternatively, take `db.LockIn(ctx, tx, "mail:"+messageID)` before `latest`, but the order still needs `seq`.
   - **Test.** Two concurrent `send` calls on one job send once, on both engines.

3. **internal/kit/connections/client.go:85-131: a rotated refresh token is lost when the caller's context ends.** `refresh` runs its transaction, the provider call and the `UPDATE` on the request's context (`RoundTrip` passes `req.Context()`, client.go:167).
   - `database/sql` rolls back a transaction whose context is cancelled. So if the client disconnects, the request times out, or a job loses its lease or shuts down after the provider has rotated the token, the new refresh token is discarded and the old one is already dead.
   - Probe: a transport cancels the caller's context right after `/token` answers. The first call returns `context canceled`. The next refresh is refused by the provider (400; it had made 1 refresh). The connection is broken until someone reauthorises it.
   - This breaks the package's own contract (connections.go:1-2, docs/integrations.md section 4, docs/packages.md:220).

   Fix: run the whole refresh transaction on `context.WithoutCancel(ctx)` with its own timeout, below `APP_DB_LOCK_TIMEOUT` and `IDLE_TX_TIMEOUT`. Return the caller's context error only after the commit. If the write fails after a successful provider call, log it at error level with the connection id (never the token). Test: cancel the caller's context after the token response, then check that the stored refresh token is the rotated one.

## Should-fix

1. **connections/client.go:85-114: pool exhaustion during refresh.** This is the same class of bug as P3b.
   - The refresh holds a pool connection across the provider call. Every concurrent caller for the same connection holds another connection while it blocks on `db.Lock`.
   - With `APP_DB_MAX_OPEN=20`, twenty concurrent API calls (HTTP, or a sync lane) on an expiring connection pin the whole pool for the provider's latency. The default client timeout is 30 s.
   - That starves HTTP and job lease renewals, and failed renewals cancel handlers.
   - Waiters also hit `LOCK_TIMEOUT` (10 s, shorter than the 30 s provider timeout) and fail instead of getting the fresh token.

   Fix: put an in-process `singleflight` keyed by connection id in front of the database lock, so one process holds at most one connection per refreshing id. Bound the provider call below the lock timeout.

2. **jobs/store.go:53: on MySQL, concurrent `Unique` enqueues fail instead of deduping.** On MySQL (REPEATABLE READ), the twin lookup is a consistent read. A caller that read anything earlier in its transaction cannot see a twin committed after its snapshot. The loop then gives up with "unique key kept conflicting" and fails the caller's transaction.
   - Probe: tx1 enqueues key K and holds. tx2 runs one SELECT, then enqueues K and blocks. tx1 commits. Postgres returns the same id; MySQL returns that error.
   - Fix: on MySQL, make the twin lookup a locking read (`FOR SHARE`), which reads the latest committed row. Add this as a contract test.

3. **webhooks/deliver.go:77-88: a shutdown or lost lease is recorded as a failed attempt.** When `post` fails because the job's context was cancelled, `recordAttempt` still increments `attempts` and `failure_count`. On the final attempt it also marks the delivery `failed` and may disable the endpoint.
   - Meanwhile the queue releases the job without spending an attempt (worker.go:184-191), and the rerun returns early because the status is no longer `pending`.
   - Result: a deploy during a final attempt silently fails the delivery and can disable a healthy endpoint.
   - Fix: when `ctx.Err() != nil` after `post`, return `context.Cause(ctx)` and record nothing.

4. **seal/seal.go:64-76, connections.go:286-289, deliver.go:73: key rotation can never finish.** `Open` reports that an older key opened the value, but every caller drops that flag.
   - An old key can therefore never be removed from `APP_CONNECTION_KEYS` or `APP_WEBHOOKS_OUT_KEYS` without making tokens and secrets unreadable.
   - MFA reseals on use (docs/packages.md:143), so this is inconsistent with the rest of the kit.
   - Fix: reseal on use inside the refresh lock (connections) and on delivery (webhooks), and add a reseal command, or document the gap.

5. **connections/connections.go:125-127: the default HTTP client is not SSRF-safe.** It uses `DefaultTransport`, which means proxies from the environment, followed redirects and any destination address. docs/security.md:107 lists connections under SSRF.
   - Providers with tenant-supplied hosts (self-hosted GitLab, Shopify shop domains) would reach internal addresses.
   - Fix: move `Dialer` to a shared kit package and make it the connections default. A provider can opt out explicitly.

6. **jobs/worker.go:184-188: a lost lease requeues regardless of `max_attempts`, with `run_at = now`.** Each claim spends an attempt, but this path never checks for exhaustion.
   - A job whose renewals keep failing loops forever, past `max_attempts`, with no backoff. One cause is a handler that saturates the pool, so the renewal cannot get a connection.
   - Fix: send this path through the same exhaustion check as `fail` (fail with `lease_lost` when `Attempt >= MaxAttempts`), and apply backoff.

## Nits

1. ssrf.go:19-25: also block `::/96` (IPv4-compatible) and `168.63.129.16/32` (Azure WireServer).
2. deliver.go:105: the scheme is not re-checked at delivery time. An `http://` endpoint created while `ALLOW_HTTP` was on keeps receiving in clear text after the flag is removed.
3. webhooks.go:243-249: `RotateSecret` swaps the secret with no overlap, so receivers return 401 until they update. Standard Webhooks allows several signatures; keep the previous secret for a grace period and sign with both.
4. admin.go:140-155: `Retry` and `RetryAllFailed` raise a raw unique violation when an open twin holds the key. One conflict also fails the whole `--all-failed` batch. Clear `unique_key` on retry, or skip conflicting rows.
5. store.go:103-104 (MySQL): under REPEATABLE READ, the claim locks every row it scans. One claim held 4 record locks: the chosen job, plus a future higher-priority job ahead of it in index order. It also takes gap locks that block enqueues into the lane. Run claim and reap with `db.Isolation(sql.LevelReadCommitted)` on MySQL.
6. store.go:39 (MySQL): `ON DUPLICATE KEY UPDATE id = id` takes an exclusive lock on the open twin until the enqueuing transaction commits, which blocks that job's renewal and outcome writes. This is harmless for short transactions; note it.
7. worker.go:160-165: a kind no process handles is released every 30 s forever, and its attempt is refunded each time. Fail it after N releases, or show it in `queue:status`.
8. store.go:160-174: the reaper compares against its own host's wall clock, so the overlap bound is clock skew plus handler exit time. Document the NTP requirement next to `APP_JOBS_LEASE`.
9. config.go:32-53: nothing checks that the lane workers, plus the reaper, scheduler and renewals, fit inside `APP_DB_MAX_OPEN`. Lanes allow up to 256 workers each, and `serve` shares the pool with HTTP.
10. mail/service.go:122-124: retrying a mail job whose body was cleared reports `done` and sends nothing. Return `Permanent("body cleared")` so `queue:retry` tells the operator.
11. connections.go:245: `ids.ID[struct{}]` should use a named tag (typed-id convention).
12. connections.go:186: `oauth2.AccessTypeOffline` is Google-specific. Let `Provider` supply the auth-code options.
13. client.go:201-207: `Retry-After` given as an HTTP date is ignored, and a 401 after a fresh token is not retried after a forced refresh.
14. connections.go:303-331: two concurrent first connects of one account hit a raw unique violation. Turn it into an upsert, or retry once.
15. schedule.go:32-67: during a two-slot deploy (D32), old and new processes each rewrite a schedule's spec and `next_run_at` to their own version on start.

## For P4 (tenancy)

- **Tables that need `tenant_id`:**
  - `jobs` (nullable)
  - `mail_outbox`
  - `webhook_endpoints`, `webhook_events`, `webhook_out_deliveries`
  - `connections`
  - `oauth_states` (when a state is tenant-bound)
- **Keys that must become tenant-scoped:**
  - `jobs_open_unique` becomes `(tenant_id, unique_key)`. On Postgres use `NULLS NOT DISTINCT`. On MySQL, include `tenant_id` in the functional key. Without this, the twin lookup under row-level security cannot see another tenant's twin, and Enqueue fails with "kept conflicting".
  - `connections (provider, external_account_id)` becomes `(tenant_id, provider, external_account_id)`.
- **Jobs:**
  - `claim` must return `tenant_id`, and `Job` needs a tenant field.
  - `execute` must put the tenant into the handler's context.
  - The handler runners for `mail.send` and `webhooks.deliver` must open `Tx[Tenant]` for that tenant.
  - Queue bookkeeping (claim, renew, finish, reap, schedules, admin commands) and the `jobs.prune`, `mail.prune` and `webhooks.prune` handlers run on `InOperatorTx`.
- **Webhooks:** `Emit` relies on row-level security for its endpoint SELECT. `OnDisabled` must email that tenant's admins.
- **Connections:** `connections.PlainTx` gets a tenant runner.

## Fix pass

Each blocker was reproduced first with a test that failed on the code as reviewed, then fixed.

Blockers:
1. SSRF zone bypass: fixed. The dialer moved to the new `internal/kit/netguard` (default deny, zones refused, `%` in a host refused, IPv4-mapped and IPv4-compatible forms unwrapped), used by webhooks and connections. `TestAllowed` covers every range boundary; the dialer test dials `[::1%lo0]` and `[fe80::1%25eth0]`.
2. Mail guard: fixed. `mail_outbox.seq` with `unique (message_id, seq)` (migration amended on both engines); the latest state is the highest seq, each transition inserts seq + 1, and a conflict stops the run as uncertain without recording. No ordering by host time. `TestSend_ConcurrentRunsSendOnce` (sent twice on Postgres before).
3. Rotated refresh token lost on caller cancel: fixed by the new lifecycle (singleflight, a committed lease, the provider call detached from the caller and outside any transaction, a write retried alone). `TestRefresh_CallerCancelledAfterTheProviderAnsweredStillStores`.

Should-fix:
1. Pool exhaustion: fixed. One refresh per connection per process; no transaction or pooled connection is held across the provider call or while waiting.
2. MySQL Unique enqueue: fixed. The twin lookup on MySQL is `FOR SHARE` on the functional index expression (EXPLAIN: const lookup). `TestEnqueue_UniqueTwinCommittedDuringTheTransactionIsReturned`.
3. Shutdown or lost lease counted as a failed webhook attempt: fixed; nothing is recorded and the cause is returned. `TestDelivery_ShutdownDuringThePostIsNotAFailedAttempt`.
4. Key rotation: fixed. Webhook secrets opened with an older key are resealed on delivery; connection tokens are sealed with the newest key on every write; `webhook:rekey` and `connection:rekey` reseal the rest; procedure in security.md section 9.
5. Connections default client: now a netguard client.
6. Lost lease requeue: the worker writes nothing on a lost lease; the reaper requeues per row with the kind's backoff and fails jobs whose attempts are spent.

Nits:
- Done: 1 (`::/96` through the IPv4-compatible unwrap, `168.63.129.16/32`), 2 (`insecure_url` at delivery time), 4 (`queue:retry` gives up the unique key), 5 (`jobs.PlainTx` is read committed), 6 (noted in packages.md), 8 (NTP noted next to `APP_JOBS_LEASE`), 10 (`Permanent` when the body was cleared), 11 (connections now use `kit/oauthstate`), 12 (`AuthOptioner`; offline access is no longer added by default), 13 (`Retry-After` as a date), 14 (a concurrent first connect retries as a reconnect).
- Not done: 3 (secret overlap on rotation needs a previous-secret column and an expiry), 7 (an unknown kind is still released forever; visible in `queue:status`), 9 (pool budget check belongs in app wiring), 15 (schedule spec flip-flop during a two-slot deploy), and the forced refresh after a 401 from 13.

For P4: unchanged, still as listed above. Also `connections.refresh_owner`, `refreshing_until` and `version` need no tenant change; the rekey commands must run per tenant or on the operator pool.
