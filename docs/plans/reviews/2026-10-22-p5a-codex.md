# Blockers

- **Shutdown or lease cancellation can be recorded as success.** [internal/kit/jobs/worker.go:178](internal/kit/jobs/worker.go:178)  
  **Failure scenario:** A handler observes cancellation, performs cleanup, and returns `nil`. The `err == nil` branch runs before checking `errShutdown` or `errLeaseLost`, so the job is marked `done`. During shutdown this spends the attempt and loses the job; after lease expiry it may accept an outcome from a worker whose lease is no longer valid.  
  **Fix:** Check cancellation cause before handler error. Shutdown must call `markReleased`, lease loss must retry/drop the outcome, and only an uncancelled `nil` result may call `markDone`. Add tests where cancelled handlers return `nil`.

- **OAuth refresh can be replayed automatically after rotating the provider token.** [internal/kit/connections/client.go:85](internal/kit/connections/client.go:85), [internal/kit/connections/client.go:114](internal/kit/connections/client.go:114), [internal/kit/connections/connections.go:67](internal/kit/connections/connections.go:67)  
  **Failure scenario:** `PlainTx` uses the database layer’s automatic deadlock/serialization retry. If the provider rotates the refresh token and the update or commit then fails retryably, the entire closure runs again and calls the provider with the consumed old token. The connection is marked `needs_reauth`, while the valid rotated token from the first call is lost. The transaction also occupies a pooled connection throughout a potentially slow network call, allowing concurrent refreshes for different connections to exhaust the pool.  
  **Fix:** Never place the provider call inside an automatically replayed transaction. Use an explicit refresh state/lease with short transactions, persist the returned token without re-calling the provider, and make competing callers wait and re-read. At minimum, introduce a no-retry refresh runner and bounded refresh concurrency. Add a test injecting a retryable SQL failure after provider rotation.

- **Disconnect and reconnect do not participate in the refresh lock.** [internal/kit/connections/client.go:211](internal/kit/connections/client.go:211), [internal/kit/connections/connections.go:299](internal/kit/connections/connections.go:299)  
  **Failure scenario:** A refresh can rotate a token while `Disconnect` revokes the old token and then deletes the row, leaving the newly rotated provider credential active but untracked. Concurrent reconnect can likewise store new authorization tokens and then have the older refresh overwrite them.  
  **Fix:** Serialize refresh, reconnect, and disconnect through the same connection lifecycle protocol. Mark a versioned `disconnecting` or `refreshing` state in a short transaction, refuse competing transitions, perform network I/O outside the pool transaction, then conditionally persist or delete the unchanged version.

- **The authenticated connection client leaks tokens across redirects and arbitrary destinations.** [internal/kit/connections/client.go:145](internal/kit/connections/client.go:145), [internal/kit/connections/client.go:166](internal/kit/connections/client.go:166)  
  **Failure scenario:** The returned client uses the default redirect policy. On every redirected request, the custom transport unconditionally adds the provider token again, even if Go removed `Authorization` because the destination host changed. A provider response redirecting to an attacker-controlled host therefore receives the access token. Calling this client with any unrelated URL has the same result.  
  **Fix:** Bind each connection to provider-declared HTTPS origins/API base, reject requests outside those origins, and refuse redirects or restrict them to the exact allowed origin.

- **The SSRF blocklist permits reserved and non-globally-reachable IPv6 ranges.** [internal/kit/webhooks/ssrf.go:19](internal/kit/webhooks/ssrf.go:19), [internal/kit/webhooks/ssrf.go:35](internal/kit/webhooks/ssrf.go:35)  
  **Failure scenario:** Addresses such as benchmarking `2001:2::/48`, documentation `3fff::/20`, SRv6 SID `5f00::/16`, and broadly unallocated IPv6 space are not blocked. A literal URL in one of these ranges passes both URL validation and the final socket check. If an overlay or host route uses that range internally, a tenant can reach it. These omissions conflict with the documented policy to reject benchmarking, documentation, and reserved ranges. The ranges are identified in the [IANA IPv6 Special-Purpose Address Registry](https://www.iana.org/assignments/iana-ipv6-special-registry).  
  **Fix:** Use a default-deny routability policy: admit only currently public unicast allocations, then exclude every non-globally-reachable special-purpose prefix. Keep the table synchronized with IANA and test every admitted/blocked boundary.

- **A stale webhook worker can overwrite a newer successful delivery.** [internal/kit/webhooks/deliver.go:133](internal/kit/webhooks/deliver.go:133), [internal/kit/webhooks/deliver.go:192](internal/kit/webhooks/deliver.go:192)  
  **Failure scenario:** Worker A loses its lease during the HTTP call and worker B takes over. B can record `succeeded`, after which A records `pending` or `failed` because the update has no delivery fence. The delivery becomes permanently inconsistent, failure counts are incremented, and the endpoint may be disabled despite a successful newer attempt.  
  **Fix:** Store a delivery attempt generation or fencing token derived from the job attempt and update only when it is newer than the stored generation. Only the winning update may alter endpoint failure counts or trigger disable notification. Test out-of-order completion of two attempts.

# Should-fix

- **Sensitive mail payloads remain stored after an uncertain delivery.** [internal/kit/mail/service.go:131](internal/kit/mail/service.go:131), [internal/kit/mail/service.go:160](internal/kit/mail/service.go:160)  
  **Failure scenario:** An SMTP connection can fail after the server accepted a reset or invite email. The attempt becomes terminally `uncertain`, but `ClearPayload` runs only for `sent`, leaving the usable token in the jobs table for the full body-retention period. The crash-recovery `sending -> uncertain` path has the same issue.  
  **Fix:** Clear sensitive payloads atomically whenever a message enters either `sent` or terminal `uncertain`, since neither state will be retried.

- **Mail outbox ordering relies on application clocks.** [internal/kit/mail/service.go:184](internal/kit/mail/service.go:184), [internal/kit/mail/service.go:208](internal/kit/mail/service.go:208)  
  **Failure scenario:** `latest` orders by microsecond-truncated host time and UUID. Clock skew between replicas, or equal timestamps, can cause an older `failed` or `sending` row to sort after `sent`. Following an outcome loss or operator retry, the service may resend a message that was already accepted.  
  **Fix:** Give transitions a per-message monotonic sequence or maintain a locked current-state row alongside the append-only attempt log. Never infer state-machine order from host timestamps.

- **Provider adapter errors can expose response bodies or tokens.** [internal/kit/connections/connections.go:219](internal/kit/connections/connections.go:219), [internal/kit/connections/client.go:233](internal/kit/connections/client.go:233)  
  **Failure scenario:** `Account` and `Revoke` errors are wrapped verbatim. An adapter or HTTP helper may include response bodies, authorization headers, account data, or tokens; these errors can then reach API responses or logs. This violates the brief’s safe-error requirement.  
  **Fix:** Define safe provider error codes/sentinels and return only classified messages across the package boundary. Do not wrap arbitrary provider errors into caller-visible errors.

- **Webhook endpoint mutations ignore optimistic concurrency.** [internal/kit/webhooks/webhooks.go:242](internal/kit/webhooks/webhooks.go:242), [internal/kit/webhooks/webhooks.go:259](internal/kit/webhooks/webhooks.go:259), [internal/kit/webhooks/webhooks.go:270](internal/kit/webhooks/webhooks.go:270)  
  **Failure scenario:** Two concurrent secret rotations both succeed and return different secrets, while only the last stored secret works. Enable and delete operations similarly accept stale state despite the row carrying `version`.  
  **Fix:** Require the expected version for every endpoint mutation and use `WHERE id = ? AND version = ?`; map zero affected rows to the standard stale-write conflict.

- **Secret-decryption failure leaves a webhook delivery falsely pending.** [internal/kit/webhooks/deliver.go:73](internal/kit/webhooks/deliver.go:73)  
  **Failure scenario:** If an old encryption key is removed too soon or ciphertext is corrupted, the job fails permanently but `webhook_out_deliveries` remains `pending` with zero recorded attempts. Operators see a delivery that appears runnable although no job will retry it.  
  **Fix:** Record a terminal `failed` delivery with a safe `secret` error code before returning the permanent job error.

# Nits

- **P4 tenancy follow-up is still required by design.** [db/migrations/postgres/20261022173122_kit_jobs.sql:2](db/migrations/postgres/20261022173122_kit_jobs.sql:2), [db/migrations/postgres/20261022173125_kit_mail_outbox.sql:2](db/migrations/postgres/20261022173125_kit_mail_outbox.sql:2), [db/migrations/postgres/20261022173127_kit_webhook_endpoints.sql:2](db/migrations/postgres/20261022173127_kit_webhook_endpoints.sql:2), [db/migrations/postgres/20261022173131_kit_connections.sql:2](db/migrations/postgres/20261022173131_kit_connections.sql:2)  
  **Failure scenario:** Merely adding `tenant_id` later would leave global dedupe/account uniqueness, non-leading indexes, and workers that do not restore tenant transactions.  
  **Fix:** P4 must tenant-scope `jobs`, `mail_outbox`, all outbound webhook tables, `connections`, and connection OAuth state; update unique/index/FK/RLS definitions in both dialects; carry and restore tenant context through enqueue, claim, mail, delivery, replay, OAuth finish, refresh, and disconnect paths; keep global schedules/operator maintenance explicit.

# Verdict

**fix-then-ship**

# Fix pass

Each blocker was reproduced first with a test that failed on the code as reviewed, then fixed.

- Cancellation recorded as success: fixed. The cause is checked before the handler's result: shutdown releases without spending the attempt, a lost lease writes nothing (the reaper requeues with backoff, or fails when attempts are spent), and only an uncancelled nil is `done`. `TestShutdown_CancelledHandlerReturningNilIsReleased`.
- Refresh replayed after rotation: fixed. A committed lease (`refresh_owner`, `refreshing_until`, `version`) in a short transaction; the provider call outside any transaction; the write conditioned on owner and version and retried alone (on retryable errors and uncertain commits, with a check whether its own commit landed). `TestRefresh_RetryableWriteFailureAfterRotationKeepsTheRotatedToken`.
- Disconnect and reconnect outside the lock: fixed. Both wait while a lease is live; disconnect marks `disconnecting` at a new version, revokes outside transactions, and deletes at that version; a refresh whose write loses revokes the token it got. `TestDisconnect_DuringRefreshLeavesNoLiveToken`.
- Token leak across redirects and origins: fixed. Providers declare `APIOrigins` (https, or http on loopback); the transport refuses other origins before adding the token, and redirects are followed only within the same origin. `TestClient_TokenOnlyReachesTheProviderOrigin`, `TestNew_APIOriginsMustBeHTTPSOrLoopback`.
- IPv6 reserved ranges: fixed in `internal/kit/netguard` with a default-deny policy (IPv4 public unicast outside the non-reachable IANA blocks; IPv6 only in `2000::/3` outside them; 6to4, Teredo, NAT64 refused outright; zones refused). `TestAllowed` covers every boundary.
- Stale webhook worker overwriting a newer outcome: fixed. `webhook_out_deliveries.generation` takes the job attempt; an outcome applies only when newer, and only the winning write touches the endpoint. `TestDelivery_OnlyANewerAttemptRecordsItsOutcome`.

Should-fix:
- Sensitive mail after uncertain: fixed; the body is cleared in the transaction that records `sent` or a final `uncertain`, including the crash-recovery path (asserted in the two uncertain tests).
- Mail ordering by clocks: fixed with `seq` and `unique (message_id, seq)`.
- Provider errors: fixed; only `ErrProviderUnavailable` or `ErrProviderFailed` with the operation and an RFC 6749 code or HTTP status cross the boundary, and nothing raw is logged.
- Endpoint mutations: rotate, enable, the new disable, and delete take the expected version and answer `*occ.StaleError`. `TestEndpoint_ChangesAtAStaleVersionConflict`.
- Undecryptable secret: records a terminal `failed` delivery with code `secret` before the permanent job error. `TestDelivery_UnreadableSecretFailsTheDelivery`.

Known limit: the delivery generation is the job attempt, and `queue:retry` resets attempts, so retrying a deliver job whose delivery is still `pending` at a higher generation records nothing; use `webhook:replay` for deliveries.

P4 notes stay for P4; no `tenant_id` was added.
