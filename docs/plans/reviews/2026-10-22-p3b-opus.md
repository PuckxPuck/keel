# P3b review (Opus)

Scope: `internal/kit/auth` (secret, session, store, cache, resolve, throttle) and its `realm`, `password`, `tokens`, `totp`, `devices`, `devlogin` packages; the P3b parts of `rbac`, `users`, `ratelimit`, `idempotency`, `httpx`; migrations 20261022170043 to 20261022170050 (both dialects); `internal/app` (config, wiring, auth, build, access, commands). P5b packages ignored.

## Verdict

**fix-then-ship.** The session core is sound: 256-bit tokens hashed at rest, strict token shape, realm and kind checks on every lookup, revocation read from the row on every request (the cache never serves a revoked session), rotation on sign-in and MFA, `__Host-`/Secure/HttpOnly/Lax/Path=/ with no Domain, bearer only from `Authorization`, no session/device confusion. Link tokens and TOTP steps are single use under concurrency (proven below). Two blockers, both in the failure counters that D31 exists for: they can be raced past, and the password one starves the connection pool under a modest sign-in burst. Both were reproduced, not inferred.

## Blockers

1. **Failure counters check then count, so a concurrent burst skips the limit.** `internal/kit/auth/throttle.go:60-83` (`Check` is `Peek`, `Record` is a separate `Take`), used by `internal/kit/auth/password/service.go:77-108` and `internal/app/auth.go:280-300`. Every request in a burst reads the count before any of them writes it. Reproduced with a throwaway overlay test: 6 concurrent wrong passwords against a per-account limit of 3 all reached `Verify` on both Postgres and MySQL (`verified=6 throttled=0`). For TOTP it is worse because a check costs about a millisecond and has no hashing semaphore. The only cap on a burst is the in-memory `auth` class (30/min per address, per replica), so an attacker who already holds the password and has many addresses gets around 100x the intended `mfaPerUser` budget (`internal/app/wiring.go:34-35`). Fix: count the attempt atomically before checking it. `Take` first and refuse when the returned count is over the limit, so the upsert's `RETURNING hits` / `LAST_INSERT_ID` decides. Either count every attempt, or count every attempt and reset the account key on success. Add a concurrent test for each counter (password, MFA, reset request).

2. **Password sign-in holds a pooled connection while it waits on the failure counter and the hash semaphore. At pool size, every sign-in fails and other requests stall.** `Authenticate` runs inside the `signIn` transaction (`internal/app/auth.go:145-152`) and calls `failures.Check`/`Record` (`internal/kit/auth/password/service.go:78,105`). Those take a second connection from the same pool (`internal/kit/ratelimit/dbstore.go:67,70,99`; `internal/app/wiring.go:59` wires `DBStoreOf(deps.DB)`, the app pool). With N concurrent sign-ins and N >= `MaxOpen`, every transaction holds a connection and waits on `Peek` until the 2 s `dbTimeout`. Reproduced: 8 concurrent sign-ins on the 8-connection test pool gave `other=8`, all `failure counter: rate counter: context deadline exceeded`, on both engines. In production `MaxOpen=20`, so 20 concurrent sign-ins (within the per-address `auth` class) stall `Resolve` for every signed-in request too, since each one needs a connection. That is the shift-change burst D20 was written for. argon2id also runs inside the transaction, so even without the counter, 20 sign-ins queued on 4 hash slots pin 20 connections for up to a second. Fix: in `Authenticate`, take the counter outside any transaction, read the user and hash in a short read, verify with no connection held, then open the write transaction for the rehash and `Sessions.Start`. Alternatively, give `DBStore` its own small pool (D31 already says "operator pool"). Add a test with concurrency above the pool size.

## Should fix

3. **A restricted (MFA pending) session carries its full principal.** `internal/kit/auth/resolve.go:134-152` loads every grant and puts it in context. Only `Restrict` (`resolve.go:277-296`) stands between it and the permissions, and it skips public operations and anything outside Huma. `/me` returns the roles and permissions before the second factor (`internal/app/auth.go:209`). Fix: for `MFAPending`, put a principal with no grants in context (keep the user id for `/me` and the MFA endpoints), so the system fails closed by construction instead of by middleware order.

4. **A user who loses their last role can sign straight back in.** `UserAccessChanged` revokes the realm's sessions when the last role goes (`internal/kit/auth/session.go:328-337`), but `Start` (`session.go:169-193`) never checks membership. So the user gets a fresh session with an empty principal that reaches every `rbac.SignedIn()` operation (`/me`, TOTP enrol). Harmless on one realm today; on the operator realm (P4) it is a foothold. Fix: refuse `Start` when `rbac.HoldsAnyRole` is false for the realm (or make it a realm option), and answer like bad credentials.

5. **Rotation on privilege change is in the spec and the plan but not in the code.** security.md section 2 says "Rotation also happens on privilege change"; P3 lists it. `UserAccessChanged` only drops the cache. Either rotate (at minimum when the request's own principal changes its grants) or amend security.md and the plan to say what actually happens.

6. **Passwords are hashed without Unicode normalisation.** `Hash`/`Verify` work on the raw bytes (`internal/kit/auth/password/hash.go:134-150,154-182`), while the policy counts NFC runes (`policy.go:67`) and the common-list check uses raw `ToLower` (`policy.go:73`). A user whose keyboard sends a decomposed "e" plus combining accent on one device and a precomposed "é" on another cannot sign in. NIST SP 800-63B-4 asks for NFKC/NFKD before hashing. Fix: normalise (NFKC) in `Hash` and in argon2id `Verify`; for legacy bcrypt try the raw input as well, since ported hashes were made raw; normalise before the common-list lookup.

7. **The verify bounds still allow 1 GiB and t=10 per hash.** `hash.go:32-33`. With `MaxConcurrent=4`, one tampered row means 4 GiB resident and seconds of CPU per sign-in: the exhaustion the bound was meant to stop on a small host. Fix: bound stored parameters relative to the configured ones (for example memory at most 4x configured and at most 256 MiB, time at most 2x configured plus 1), since `NeedsRehash` moves rows forward anyway.

8. **The dev login request gate trusts any untrusted local proxy.** `internal/kit/auth/devlogin/devlogin.go:44-46` checks `ClientIP` is loopback and `!Proxied`. `Proxied` is true only for configured trusted proxies. A developer running ngrok or cloudflared against `127.0.0.1:8080` without `APP_PROXY_TRUSTED` (the default) gets loopback, unproxied requests from the internet, so dev login is open to anyone with the tunnel URL. Fix: also refuse when any forwarding header is present (`X-Forwarded-For`, `Forwarded`, `X-Real-IP`, `CF-Connecting-IP`, `X-Forwarded-Host`). The test at `internal/app/auth_test.go:249` only covers a trusted proxy.

9. **Reset-request is not counted by address in the database, and its timing can reveal the account.** `internal/app/auth.go:335-361` keeps a DB counter by email only; the address limit is the in-memory `auth` class, while security.md section 2 and D31 list reset requests as database counters by address and account. Separately, the notifier runs in `db.AfterCommit`, which executes synchronously before the response (`internal/kit/db/tx.go:190-194`). A real mail notifier (the `Notifier` contract at `internal/kit/auth/tokens/tokens.go:146` invites exactly that) makes known accounts answer measurably slower. Fix: add `auth.Key("reset-request-address", addr)`; make delivery a job enqueued in the transaction (architecture.md section 7 already says mail goes through jobs) and say so on `Notifier`.

10. **`user:create` reports "sent an invite", but outside local nothing is delivered and the link is gone.** `internal/app/access_commands.go:169` and `wiring.go:41-43`: the fallback `LogNotifier` withholds the token unless `APP_ENV=local`. Staging and production have no way to give the first user a password until mail exists. Fix: when no notifier is configured, print the invite link to the operator's terminal (it is their shell, not a log) or say plainly that it was not sent.

11. **`APP_SESSION_KEYS` is documented as required outside local but does not exist.** It is in docs/configuration.md under Sessions and sign-in, and security.md section 9 lists it for rotation, but nothing in `internal/app/config.go:44-48` reads or validates it. Implement it with `RequireStrong` per key and a non-local requirement, or move the row to the phase that adds signed cursors and links.

12. **MFA has no cap on consecutive failures, and pending sessions live 12 h.** Even with blocker 1 fixed, `mfaPerUser` at 20 per 15 minutes allows about 1,900 guesses a day against a 6-digit code with three accepted steps (about 0.6% a day for someone who has the password). The restricted session gets the realm's full idle and absolute expiry (`session.go:192`, `open` at 235-242). Fix: give pending sessions a short absolute expiry (10 to 15 minutes), and after a run of consecutive failures (NIST: at most 100) revoke the user's sessions and require a reset, with an audit event. This is not a third-party lockout: only a holder of the password can trigger it.

13. **Tests missed both blockers.** There is no concurrency test for any counter, no test above pool size, and no concurrent consume test for link tokens, TOTP steps or recovery codes. The behaviour holds (below), but nothing guards it. `TestNewSessions_ProductionCookiesAreHostPrefixedAndSecure` (`internal/kit/auth/auth_test.go:450`) asserts the name only, not `Secure` on an actual `Set-Cookie`. Add a table test that drives sign-in with `Secure: true` and asserts the header, plus one 429 test on the HTTP path for MFA.

## Nits

14. Cache put-after-drop: a resolve that read grants before an access change commits can `put` after the hook's `dropUser` ran, re-caching stale grants for the TTL on that replica (`internal/kit/auth/resolve.go:157-168`, `cache.go:42-56`). security.md section 3 says changes apply "on the next request". Fix: a per-user generation counter bumped by `dropUser`/`dropRealm` and checked in `put`, or amend the doc to "within the cache TTL".
15. `tokens.Consume` (`tokens.go:126-129`) and `UseRecovery` (`totp.go:278-281`) rely only on the row lock. Add `AND used_at IS NULL` to the recovery update and check `RowsAffected() == 1` in both, as a second guard.
16. `resolveDevice` drops database errors silently (`resolve.go:177-179`), while the session path logs them (`resolve.go:142-144`). Log non-`ErrInvalidToken` errors.
17. `MaxBytes = 128` bytes (`hash.go:43`) is fewer than 64 characters for most non-Latin scripts; NIST and security.md promise at least 64 characters. Cap at 128 characters, with a byte cap of 4x that, or raise the byte cap to 256.
18. `requestReset` issues reset tokens when password sign-in is disabled (`app/auth.go:327-363`); `resetPassword` then answers 404. Return early when `w.passwords == nil`.
19. Two concurrent first `Enrol` calls race the `INSERT` into `mfa_totp` and one gets a 500 (`totp.go:105-126`). Use an upsert or `loadForUpdate` after inserting a placeholder row.
20. Confirming TOTP leaves the user's other existing sessions untouched (`totp.go:135-157` through `app/auth.go:307`). Consider revoking them so a stolen session does not survive enabling MFA.
21. security.md section 2 says a reset "clears remembered devices"; there is no such concept in the code. Amend the doc.
22. An unknown client address keys every such caller into one `unknown` bucket (`ratelimit/keys.go:52-55`), so with an untrusted unix socket one client can throttle every other's sign-in to an account. This only happens on a misconfiguration, but `limits` could skip the address-scoped key when the address is unknown and rely on the address-only key.
23. `devices.Rotate` accepts any `grace` (`devices.go:160`), negative or unbounded; clamp it (for example 0 to 24 h). Pairing-code redemption has no failure counter in the kit, although D31 lists code redemption; wire one when device endpoints land.
24. Realm cookie names are validated in `realm.New` at build time, not in config `Validate`, so `config:check` passes an invalid `APP_SESSION_COOKIE` that `serve` then refuses.

## What I verified and how

- Read every file in scope plus the spec sections named in the brief (security.md sections 1, 2, 5, 10, 11; configuration.md; D8, D9, D17, D20, D21, D22, D31; architecture.md section 5; conventions; AGENTS.md).
- `go build ./...` and `go vet` on the P3b packages: clean. `keel lint` (gofumpt, golangci-lint, vet): `0 issues`.
- `GOFLAGS=-count=1 keel test --engine postgres` and `--engine mysql`, full tree with `-race`: all packages `ok` (22 s Postgres, 13 s MySQL). The auth packages each take 2 to 5 s, run in parallel, which is within budget.
- Throwaway overlay tests (`go test -overlay`, no repo edits):
  - Password counter race: limit 3 with 6 concurrent gave `verified=6` on both engines (blocker 1). At 8 concurrent, the pool size, every request failed with a context deadline on both engines (blocker 2).
  - Link token, 6 concurrent `Consume` calls: exactly 1 succeeded (Postgres).
  - TOTP, 6 concurrent `Verify` calls with the same code: 1 accepted; 6 concurrent `UseRecovery` calls with the same code: 1 accepted (Postgres).
  - I could not rerun the concurrency checks on MySQL. Between my suite run and these tests, P5b added migrations (the `jobs` generated column), and the MySQL template copy now fails (`Error 3105 ... open_unique_key`). That failure belongs to P5b, not P3b. The MySQL code paths rely on the same InnoDB locking reads, which return the latest committed row.
- Checked by reading: realm and kind mismatch leave the request anonymous and clear the realm cookie; tokens in a query string are ignored; session tokens cannot contain `.`, so the device path is reached only by `id.secret` shapes and never falls back to the session path; device tokens are refused from cookies; `PassMFA` and `End` refuse device sessions; `RecentMFA` refuses devices; the production profile forces `__Host-` and `Secure` through `Env.IsProd()` (staging included); MFA keys need 32 bytes and no example value in production; argon2 below OWASP's minimum is refused in production; HKDF-SHA256 per key, AES-GCM with a random 96-bit nonce, user id as AAD, and a reseal under the newest key on use; recovery codes are 80-bit, salted and hashed. The migrations are expand-only, one statement per MySQL file, with check constraints that match the Go constants.

## Fix pass (2026-10-22)

Every blocker, should-fix and nit is fixed. Tests were written alongside the fixes, not ahead of them; the overlay reproductions above stand as the failing runs, and the new tests fail on the old behaviour by construction (they assert counts and outcomes the old code could not meet).

1. Fixed. `auth.Failures` is take-first: `Attempt` counts every counter with the upsert that returns the count and refuses over a limit; `Succeeded` clears the account counter and refunds the address one; `DBStore.Peek` is gone (`Reset`, `Refund` added). Concurrent tests on both engines: password (`TestAuthenticate_Burst`, 12 at a limit of 3 gives 3 hash checks), MFA (`TestMFA_AttemptsAreCountedAndAStreakRevokes`, 8 at 5 gives 5 checks and 3 x 429), reset requests (`TestPasswordReset_AnswersAlikeCountsAndRevokesSessions`, 8 at 5 gives 5 links).
2. Fixed. `password.Service.Authenticate(ctx, d, email, plain, then)`: counter first on its own statement, user and hash in a short read-only transaction, verify with nothing held, then one write transaction for the rehash and `then` (the session). `Prepare` hashes new passwords before their transaction. `TestAuthenticate_Burst` signs in 12 at once on the 8-connection test pool.
3. Fixed. A pending session's principal is the user with no grants; `/me` answers `mfaRequired: true` with no user, roles or permissions.
4. Fixed. `Start` refuses with `auth.ErrNoAccess` when the user holds no role in the realm; sign-in answers it as `invalid_credentials`.
5. Fixed with `users.access_version`, moved in the same transaction by grants, revocations, role permission changes and deletions, status changes and password changes. Resolve reads it with the session row; a mismatch rotates a browser session (new cookie, old token dead) and records the version on a bearer session. security.md sections 2 and 3 describe it.
6. Fixed. NFKC before argon2id hashing and verifying; bcrypt tries raw then NFKC; length and the common list use the normalised form.
7. Fixed. Stored parameters are bounded relative to the configured ones (memory at most 4x and 256 MiB unless the configured is higher, time at most 2x+1, four lanes), `ErrOutOfBounds` with a logged error and a dummy verify. `APP_PASSWORD_MEMORY_BUDGET` (256 MiB) bounds memory times max concurrent.
8. Fixed. Dev login also needs a loopback Host and no forwarding header (an operation middleware); tests cover a tunnel's public Host and its forwarding headers.
9. Fixed. DB counters by address and by account; the notifier is called inside the issuing transaction and only enqueues (`Notifier` takes the `db.Transaction`); a 250 ms response floor on every path.
10. Fixed. `user:create --print-link` prints the invite token to the terminal; without it and without a notifier outside local the command refuses, and `serve` refuses to start.
11. Fixed. `APP_SESSION_KEYS` (base64, at least 32 decoded bytes each, newest first, required outside local); `Config.SigningKeys()` for paging and files; the device list's cursors use it.
12. Fixed. Pending sessions live ten minutes; ten wrong codes in a row revoke every session with `mfa.failure_limit_reached`.
13. Fixed. Concurrency tests above, `TestStart_ProductionCookieHeader` asserts the `Set-Cookie` header, the MFA test asserts 429 with `Retry-After`; concurrent consume tests for link tokens and recovery codes.
14. Fixed by item 5: the cache key includes the access version.
15. Fixed. Both spends check `used_at IS NULL` and exactly one row.
16. Fixed. Non-`ErrInvalidToken` device errors are logged.
17. Fixed. 128 characters and 512 bytes, in the schema and the service.
18. Fixed. 404 when password sign-in is off.
19. Fixed. Enrol is one upsert that never touches a confirmed row.
20. Fixed. Confirming TOTP revokes the user's other sessions.
21. Fixed in security.md (no remembered devices; reset revokes all sessions).
22. Fixed. Address-paired keys are skipped when the address is unknown.
23. Fixed. Grace clamped to 0 to 24 h; device operations (pairing codes, pair, list, rotate, revoke) with a DB counter on redemption; pairing codes and rotate/revoke are realm-bound.
24. Fixed. Cookie names are validated in config.
