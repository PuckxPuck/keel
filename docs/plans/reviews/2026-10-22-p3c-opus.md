# P3c review (Opus)

Scope: `internal/kit/oauthstate`, `internal/kit/auth/oidc`, `internal/kit/auth/passkey`, `internal/kit/apikeys`; the P3c parts of `auth/session.go`, `auth/realm/realm.go`, `httpx/httpx.go` (Mirror, SpecPath) and `ratelimit` (api-key, api-tenant, OneTenant); `internal/app/{signin,apikeys,apikey_commands,build,wiring,config,access,auth,ping,commands}.go` and `apirealm_test.go`; `cmd/keel/steps.go` (oasdiff); migrations 20261022181501 to 20261022181504 on both dialects. P5a packages ignored.

## Verdict

**fix-then-ship.** The security core is right. OIDC binds state to the browser by cookie before it spends anything, spends the state in its own committed transaction, uses PKCE S256, checks nonce in constant time, checks iss/aud/exp through go-oidc plus iat (5 min ahead, 10 min old) and azp itself, and sends every return path through SafeReturnPath. Passkeys spend the challenge first, require UV at registration and sign-in, refuse a non-advancing sign count, and check the user handle against the stored owner. API keys reject a bad checksum before the database, compare SHA-256 in constant time, read the row on every request (D34, no cache), check the allowlist through `httpx.ClientIP`, and enforce the scope guardrail on global grants only. The api realm mirrors only `Public` operations, runs no session, CSRF or CORS middleware, and enforces `Need` with a realm match. Two blockers, both the pooled-connection rule the P3b fix pass set and the brief repeats. I reproduced both; neither is inferred.

## Blockers

1. **OIDC start holds a pooled connection across provider discovery.** `internal/app/signin.go:89-93` opens `db.InTx` and calls `oidc.Service.Start`, which calls `discover` first (`internal/kit/auth/oidc/oidc.go:218`). `discover` makes an outbound HTTP call (15 s client timeout) under `s.mu` (`oidc.go:180-200`), and a failure is not cached, so every start retries it. Reproduced with an overlay probe and an issuer that hangs: 5 concurrent `GET /auth/oidc/start` from 5 addresses gave `InUse` 0 -> 5 on both engines, each connection idle in a transaction until discovery returned. If the IdP slows down or fails while users are signing in, the pool drains (MaxOpen 20, `auth` class 30/min per address), and every other request stalls behind it, sessions included. Fix: call `discover` before opening the transaction. Either split `Start` into `Prepare(ctx)` (discovery, no tx) and `Put`, or have `Start` take the `oauthstate.Runner` and open its own short transaction after discovery. A short negative cache (for example 30 s after a failed discovery) stops a down IdP from costing 15 s per attempt.

2. **`last_used` touch waits on the key's row lock while holding a pooled connection.** `internal/kit/apikeys/apikeys.go:273-276,287-298` runs a blocking `UPDATE` inside the per-request resolve transaction (`internal/app/wiring.go:112-117`, `apikeys/public.go:164-168`). Any transaction that holds the key row makes every request on that key that needs a touch (all of them once `last_used_at` is a minute old) wait with a connection checked out: `Revoke`, `ReportLeaks`, `MarkReminded` in the P5 reminder job, a future rescope. Reproduced: with one transaction holding an `UPDATE` on the key row, 5 concurrent `GET /v1/ping` with that key went `InUse` 1 -> 6 on both engines and each took about 700 ms, the lock holder's lifetime. A reminder job that marks many keys in one transaction pins a connection for every in-flight request on those keys. The brief requires that last_used updates not hold a pooled connection while waiting on another. Fix: make the touch non-blocking. `SELECT id FROM api_keys WHERE id = ? AND (last_used_at IS NULL OR last_used_at <= ?) FOR UPDATE SKIP LOCKED`, and run the `UPDATE` only when a row comes back (both engines support SKIP LOCKED; `jobs` already relies on it). Add a concurrent test with a held row lock.

## Should fix

3. **The ID token verifier accepts RS256 only.** `oidc.go:293` builds `gooidc.NewVerifier` directly with an empty `SupportedSigningAlgs`, which go-oidc defaults to RS256 (`go-oidc/v3/oidc/verify.go:300-304`). The provider's advertised `id_token_signing_alg_values_supported` is only applied by `Provider.Verifier`/`VerifierContext` (`verify.go:136-144`). An IdP that signs with ES256 or PS256 fails every sign-in with a 401. Fix: use `p.VerifierContext(base, cfg)`, or copy the provider's algorithms into the config. Keep the RemoteKeySet built from the WithoutCancel context.

4. **Email-trusted linking lets a recycled address take over the old account.** `oidc.go:351-370` links any new subject whose verified email matches an active user, even when that user already has an identity from the same issuer under another subject. When an organisation reassigns `ann@corp` to a new hire (new `sub`, same verified email), the new hire signs in as Ann. Fix: in `Link`, refuse (ErrRefused) when the matched user already has an identity for `c.Issuer`. A changed subject then needs the app's Corroborator or an admin. One table row in `TestSignIn` covers it.

5. **Passkeys cannot be listed or removed.** No operation or service method deletes a passkey. A passkey sign-in counts as both factors (`internal/app/signin.go:240`, `auth/session.go:209`), so a lost or compromised authenticator stays a full credential until someone edits the database. Add `GET /auth/passkeys` and `DELETE /auth/passkeys/{id}` (own passkeys, full session; audit `passkey.removed`; revoke other sessions like registration does), plus an operator command to remove all of a user's passkeys.

6. **P4 cannot resolve a key under RLS as designed.** `apikeys.TxRunner` (`public.go:123`) says "plain, or the tenant's under tenancy", but the tenant is only known after the key row is read, and with RLS on `api_keys` a tenant-less app-role transaction sees no row. `ReportLeaks` (`internal/app/apikeys.go:166-173`) and `DueForReminder` need to cross tenants, yet the leak endpoint sits on the tenant realm, which D29 keeps away from the operator pool. Decide now and write it into the P4 plan: for example a global `api_key_tenants (key_id, tenant_id)` lookup with no personal data and no RLS, read first, then `Resolve` in that tenant's transaction; leak reports and reminders run as operator-pool jobs. `OneTenant` (`ratelimit/limiter.go:74`) becomes a by-tenant key from the resolved key.

7. **Passkeys and OIDC identities are realm-blind.** `passkeys` and `identities` carry no realm, and a passkey sign-in starts with MFA passed in whichever realm the request reached. Today only the tenant realm exists, so nothing is exposed. When P4 adds the operator realm with `MFA=required`, a passkey a user registered on a tenant realm with MFA off (password only) will satisfy operator MFA. Before the operator realm mounts these operations, record the realm a passkey was registered on and accept it only there, or make "passkey counts as MFA" a per-realm setting that defaults to off for operator.

8. **`keel check` lets warning-level breaking changes through.** `cmd/keel/steps.go:90` uses `--fail-on ERR`. integrations.md section 2 says "with no exceptions"; oasdiff reports some client-breaking changes (for example a removed optional response property) as WARN. Use `--fail-on WARN`. Probed: removing `/v1/ping` from a copy fails with `api-path-removed-without-deprecation`, exit 1, so the step itself works.

9. **The wrong-secret path has no test.** `internal/kit/apikeys/apikeys_test.go:135-136` replaces the last 7 characters, which breaks the checksum, so `Parse` refuses before the database and the constant-time compare is never reached. Build the forged key with the same id, a different secret and a valid checksum (`format.newKey(k.ID.UUID())` from an internal test, or recompute `checksum`). I ran exactly that as a probe and `Resolve` refuses it correctly on both engines; the suite should pin it.

## Nits

10. **Classes set RateLimit headers only on refusal.** `ratelimit/limiter.go:178-184`. A plugin only sees the operation class's policy (`limiter.go:130`), never the `api-key` budget that will stop it. Integrations.md says the headers exist "so plugins can back off". Set the tightest class's headers on success too.
11. **Invalid keys cost a DB read before any per-key limit.** `build.go:124-125` resolves before `Classes`. A forger can compute the CRC, so the checksum only stops typos. Only `pre-auth` by address bounds it. That is acceptable for now; if it matters, add a pre-resolve class keyed by the parsed key id for refusals.
12. **The leak report records only the first report of a key.** `apikeys/leak.go:82-84` returns before the audit write when the key is already revoked, so a second sighting at another URL is not recorded, and replays are never recorded through `Verifier.Seen` (`internal/app/apikeys.go:153-175`). Idempotent and harmless, but the threat model lists a replay store for webhook senders. Record `apikey.leaked` for every true positive, or note the choice in integrations.md.
13. **The api document declares no security scheme.** Probe of `app openapi --realm api`: there is no `components.securitySchemes` and no `security`. Clients generated from it will not send the bearer key. Add a bearer scheme to the api realm's document.
14. **Concurrent first sign-ins of one subject fail with 500.** Both insert into `identities`, and the second hits the unique key (`oidc.go:371-375`). Map the unique violation to a retry of `linkedUser`.
15. **Stale wording.** `docs/stack.md:68` says oasdiff checks `spec/openapi.yaml`; it is `spec/api.openapi.yaml`. `docs/plans/2026-10-22-keel-v1.md:126` still says "revoke and principal-cache drop" (D34 replaced it).
16. **A user can only be linked by email trust.** With `APP_OIDC_EMAIL_TRUSTED=false` and the default Corroborator, nobody can ever link, because there is no signed-in "connect provider" flow, even though `oauthstate.New.UserID` exists for it. Fine per spec, but worth a line in security.md so apps know they must supply one.

## P4 must touch

`api_keys` (tenant_id, composite keys, RLS, and the pre-tenant lookup in item 6), `apikeys.Resolve`, `Middleware` and `ReportLeaks` (tenant from the key, operator path for leaks), `DueForReminder` (per-tenant job), `ratelimit.OneTenant` (by tenant), and the tenant-scoped audit actor. `identities`, `passkeys` and `auth_challenges` follow `users` (global) unless OIDC providers become per tenant; realm binding is item 7. `oauth_states` stays global for sign-in and gains tenant scoping only for `connections`.

## Fix pass (2026-10-23)

Both blockers were reproduced with a failing test on the old code before the fix (`TestOIDC_DiscoveryHoldsNoConnectionAndAFailureIsRemembered`: 3 connections in use while discovery hung and 4 discovery calls; `TestResolve_RecordingUseNeverWaitsOnARowLock`: context deadline exceeded on both engines). Both pass now.

1. Fixed. `oidc.Service.Start(ctx, returnTo)` discovers first and then opens its own short transaction for the state; `Finish` discovers before spending the state; the exchange and key fetch run with no transaction. A failed discovery is cached for 30 s. Test with a hanging issuer checks `InUse` is 0 and the provider is asked once.
2. Fixed. The touch takes the row `FOR UPDATE SKIP LOCKED` (both engines) and skips the write when nothing comes back. Test holds the row lock and resolves within a deadline.
3. Fixed. The verifier comes from `Provider.Verifier`, so the provider's advertised algorithms and cached key set apply. The test issuer (`oidc/oidctest`) signs ES256 only.
4. Fixed. `Link` refuses a user who already has an identity from the issuer under another subject. Row in `TestSignIn`.
5. Fixed. `GET /auth/passkeys`, `PATCH /auth/passkeys/{id}` (rename at a version, 409 when stale) and `DELETE /auth/passkeys/{id}` (audits `passkey.removed`, ends the user's other sessions, 409 `passkey_last_factor` when it would leave an MFA-required realm with no second factor). No operator command; not in the brief's decision. App-level tests for the OIDC callback and passkey sign-in, list and removal.
6. Decided and documented (tenancy.md "API keys", integrations.md): `apikeys.Locator` finds the tenant from the key id (`NoTenancy` now; P4 reads a global `api_key_tenants`), then `TxRunner(ctx, tenant, fn)` opens that tenant's transaction for `Resolve`. Leak reports and reminders run as operator-pool jobs under tenancy. No tenant tables added.
7. Fixed. `passkeys.realm` and `identities.realm`; a passkey signs in only on its realm; `APP_OIDC_REALMS` (default `tenant`) enables OIDC per realm, and an identity signs in only on the realm it was linked on.
8. Fixed. `--fail-on WARN`.
9. Fixed. The test forges a key with the same id, another secret and a valid checksum.
10. Fixed. `Classes` and the operation class add their `RateLimit-Policy` and `RateLimit` entries on success too.
11. Left as is, as the review allows: `pre-auth` by address bounds it.
12. Fixed with Codex 1: the delivery id is recorded with `Seen` in the revoke transaction; a re-report of a revoked key is audited once as `apikey.leak_reported`.
13. Fixed with Codex 3: bearer scheme `apiKey` declared and attached to non-public operations.
14. Fixed. The link insert ignores a conflict and follows the winning row (read `FOR SHARE`); a different user is a normal refusal. Concurrent test.
15. Fixed (stack.md, v1 plan).
16. Fixed (security.md).
