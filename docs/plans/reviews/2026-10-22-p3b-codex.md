# P3b Codex review (scoped run, session 01a164a5-7cab-77a2-8c74-dcead0700411)

## Findings

### Blocker

1. **Dev login can be exposed through a local reverse proxy or tunnel.**  
   [internal/kit/auth/devlogin/devlogin.go:43](<internal/kit/auth/devlogin/devlogin.go:43>), [internal/kit/auth/devlogin/devlogin_test.go:53](<internal/kit/auth/devlogin/devlogin_test.go:53>)  
   `Allowed` trusts a loopback peer whenever `httpx.Proxied` is false. An unconfigured local proxy appears as a direct loopback client; the test explicitly permits forwarding headers from such a peer. If a tunnel or reverse proxy exposes the loopback listener, a remote caller can sign in as any user.  
   **Suggested fix:** Require an independent high-entropy development credential and reject any forwarding headers. Prefer mounting dev login on a separate, non-proxied development listener instead of the main router.

### Should-fix

2. **Concurrent token issuance can leave multiple password-reset tokens valid.**  
   [internal/kit/auth/tokens/tokens.go:74](<internal/kit/auth/tokens/tokens.go:74>), [Postgres migration:12](<db/migrations/postgres/20261022170045_kit_auth_tokens.sql:12>), [MySQL migration:11](<db/migrations/mysql/20261022170045_kit_auth_tokens.sql:11>)  
   Two transactions can both retire the previously visible rows and then insert new unused tokens. The schema has only a non-unique `(user_id, purpose)` index, so both may commit. Consuming one reset token does not invalidate its concurrently issued sibling, which can reset the password again later.  
   **Suggested fix:** Represent the current token as one atomically upserted row keyed by `(user_id, purpose)`, or add a database-enforced single-active-token invariant with conflict retry on both engines.

3. **Permission revocation can be served from cache after the revoking transaction commits.**  
   [internal/kit/auth/resolve.go:157](<internal/kit/auth/resolve.go:157>), [internal/kit/auth/cache.go:15](<internal/kit/auth/cache.go:15>), [internal/kit/auth/session.go:326](<internal/kit/auth/session.go:326>)  
   Invalidation is process-local, so another replica retains removed grants for the TTL. There is also a fill/invalidate race: a request can load the old principal, the revocation commits and drops the cache entry, then the request inserts the old principal afterward.  
   **Suggested fix:** Add a database-backed authorization version updated in the same transaction and include it in cache validation, or remove positive permission caching. Process-local eviction alone cannot provide revocation semantics.

4. **The Argon2 verification ceiling still permits catastrophic resource use.**  
   [internal/kit/auth/password/hash.go:30](<internal/kit/auth/password/hash.go:30>), [internal/kit/auth/password/config.go:19](<internal/kit/auth/password/config.go:19>)  
   A PHC string may request 1 GiB, ten passes and sixteen lanes. Configuration permits up to 256 concurrent hashes, giving an accepted theoretical memory demand of 256 GiB. Requests targeting an imported, corrupted, or maliciously modified hash can exhaust the process.  
   **Suggested fix:** Enforce a small allowlist or strict memory-time-product ceiling for stored hashes, and validate `memory × MaxConcurrent` against an explicit process budget.

5. **Sign-in timing equalization is bypassed by oversized passwords and legacy hashes.**  
   [internal/app/auth.go:38](<internal/app/auth.go:38>), [internal/kit/auth/password/hash.go:154](<internal/kit/auth/password/hash.go:154>), [internal/kit/auth/password/service.go:81](<internal/kit/auth/password/service.go:81>)  
   The API accepts up to 512 characters, but verification immediately returns for inputs over 128 bytes. An unknown account then performs one lookup while a known account performs the additional credential lookup, without dummy hashing to mask it. For normal inputs, supported bcrypt or older Argon2 costs can also differ substantially from the current dummy hash.  
   **Suggested fix:** Ensure every failed attempt performs a bounded current-cost dummy operation, including oversized inputs and malformed/legacy hashes, then apply a minimum response-time floor. Align transport validation with the 128-byte service limit.

6. **Password-reset requests remain timing-distinguishable.**  
   [internal/app/auth.go:325](<internal/app/auth.go:325>)  
   Unknown or disabled accounts stop after lookup, while active accounts retire and insert tokens, write audit data, commit, and invoke the notifier after commit. A real notifier can make the difference especially pronounced despite identical 204 responses.  
   **Suggested fix:** Enqueue an indistinguishable reset-request job for every normalized address and perform lookup, issuance and delivery asynchronously. At minimum, remove notifier I/O from the response path and enforce a uniform response floor.

7. **The fallback notifier either logs live authentication tokens or silently drops them.**  
   [internal/kit/auth/tokens/tokens.go:153](<internal/kit/auth/tokens/tokens.go:153>), [internal/app/wiring.go:40](<internal/app/wiring.go:40>)  
   Local mode writes reset, verification and invite tokens to logs. Outside local mode, a missing notifier is replaced with a logger that claims a link was sent but delivers nothing.  
   **Suggested fix:** Never log raw tokens. Use an explicit, loopback-protected development inbox or test notifier, and fail startup outside development when no delivery notifier is configured.

No edits were made. This was a static review of only the requested files.

# Appendix: first run (session 01a164a5-21a8-7921-acd3-b60f5ea3c05c), drifted out of scope

Codex reviewed P2 modules (rbac, users, idempotency, ratelimit, webhook, audit) instead of P3b. Only finding 6 (realm host parsing) is in P3b scope.

## Findings

1. **Blocker — [internal/kit/rbac/store.go:105](internal/kit/rbac/store.go:105) — Role grants bypass authorization, guardrails, and realm isolation.** `Access.Grant` accepts neither the acting principal nor an expected realm and inserts any supplied `role_id`. Consequently, tenant-realm code can grant an operator-realm role, callers can grant permissions they do not hold, and users can edit their own grants. The guardrail functions are not connected to this write path.  
   **Suggested fix:** make the raw insert private/bootstrap-only. Expose an actor-aware, realm-bound service that loads the role and current grants under a realm access lock, checks the actor’s realm and permissions, runs guardrails using database-loaded facts, writes, and audits atomically.

2. **Blocker — [internal/kit/users/service.go:51](internal/kit/users/service.go:51) — Disabling a user bypasses the last-administrator invariant.** `SetStatus` can disable the final holder of `access.manage`; it has no actor or access-policy input. A holder of only `users.manage` could therefore disable the sole access administrator and permanently lock out access management.  
   **Suggested fix:** route access-managed status changes through an RBAC orchestration service that locks the realm’s access state, checks the acting principal, counts other active holders, refuses the last-holder transition, then updates and audits in the same transaction.

3. **Blocker — [internal/kit/idempotency/middleware.go:177](internal/kit/idempotency/middleware.go:177) — Idempotency keys are scoped too broadly and can replay responses across security boundaries.** Signed-in keys use only `user_id`, omitting the principal’s realm; anonymous callers without a valid resolved address all become `a:unknown`. The same global `(principal, idem_key)` uniqueness can therefore replay an operator response in another realm or replay one unknown caller’s response to another. P4 tenancy would introduce the same problem across tenants.  
   **Suggested fix:** scope records by realm, tenant where applicable, and concrete credential/actor identity. Refuse idempotency-protected anonymous requests when no trustworthy address exists instead of sharing `a:unknown`.

4. **Blocker — [internal/kit/idempotency/middleware.go:126](internal/kit/idempotency/middleware.go:126), [internal/kit/idempotency/store.go:40](internal/kit/idempotency/store.go:40) — A committed operation can be executed again.** The handler’s business transaction and response complete before `finish` runs in a separate transaction. If persistence fails, the code releases the key; if the process dies, the key is automatically reclaimed after two minutes. Either path re-executes an already committed change. The first response is also streamed to the client before the replay record is durable.  
   **Suggested fix:** never automatically reclaim a claim whose business outcome is unknown. Buffer the response, persist it before sending, and leave failed finalizations indeterminate until the full TTL. For strong idempotency, finalize an operation marker in the same transaction as the domain change.

5. **Blocker — [internal/kit/ratelimit/limiter.go:140](internal/kit/ratelimit/limiter.go:140), [internal/kit/ratelimit/limiter.go:151](internal/kit/ratelimit/limiter.go:151) — Fail-closed rules fail open in pre-auth and plain-HTTP middleware.** `take` returns `ok=false` when a `FailClosed` store fails, but both paths only refuse when `ok && !Allowed`; otherwise they call the handler. A database outage therefore disables fail-closed brute-force protection.  
   **Suggested fix:** handle `!ok` with a 503 and return, matching the operation middleware. Add failing-store tests for all three middleware paths.

6. **Should-fix — [internal/kit/auth/realm/realm.go:127](internal/kit/auth/realm/realm.go:127) — Malformed bracketed DNS hosts bypass exact realm matching.** `strings.Trim(host, "[]")` turns `[ops.example.test]` or repeated-bracket variants into the configured operator host. Go’s HTTP host validation is deliberately lenient enough to admit these bytes, so an operation can answer on a host not declared for its realm.  
   **Suggested fix:** parse and validate the authority strictly. Strip brackets only for a successfully parsed IPv6 literal, validate ports, and reject malformed authorities rather than canonicalizing them into an allowed host.

7. **Should-fix — [internal/kit/idempotency/middleware.go:107](internal/kit/idempotency/middleware.go:107) — Request identity excludes the query string.** Two requests with the same method, path, body, and key but different query parameters are treated as identical and the first response is replayed. Query parameters commonly alter actions, filters, or representation.  
   **Suggested fix:** include a canonicalized query string and any behavior-affecting content headers in the request hash.

8. **Should-fix — [internal/kit/idempotency/middleware.go:188](internal/kit/idempotency/middleware.go:188) — Response capture is unbounded and can store a truncated response.** Every response is copied into a `bytes.Buffer` with no limit. Concurrent large responses can exhaust memory, and MySQL’s `mediumblob` will fail above its limit. Because `io.MultiWriter` writes to the client first, a client-write failure can leave only a partial body to persist and replay.  
   **Suggested fix:** impose a configured response limit and reject idempotency on streaming/download operations. Buffer before writing to the network, persist successfully, then flush the complete response.

9. **Should-fix — [internal/kit/webhook/webhook.go:149](internal/kit/webhook/webhook.go:149), [db/migrations/postgres/20261022153804_kit_webhook_deliveries.sql:2](db/migrations/postgres/20261022153804_kit_webhook_deliveries.sql:2) — Replay IDs are global rather than sender-scoped.** Standard Webhooks IDs are not guaranteed unique between independent senders. One valid source can reserve an ID used by another source, causing the latter’s valid event to be discarded as a replay.  
   **Suggested fix:** pass a stable source or endpoint identifier to `Seen` and use `(source_id, delivery_id)` as the primary key.

10. **Should-fix — [internal/kit/webhook/webhook.go:120](internal/kit/webhook/webhook.go:120) — Arbitrarily weak webhook secrets are accepted.** Any nonempty decoded value, including a one-byte HMAC key, passes validation. This turns configuration mistakes into trivially forgeable signatures.  
    **Suggested fix:** enforce an appropriate decoded entropy minimum, or require production configuration validation to reject weak keys before constructing the verifier.

11. **Should-fix — [internal/kit/audit/store.go:118](internal/kit/audit/store.go:118) — Chain verification silently ignores unchained audit rows.** `Verify` selects only rows where `hash IS NOT NULL`. A direct insert or accidental recorder configured without chaining can add fabricated rows between chained rows while verification still succeeds.  
    **Suggested fix:** when verifying a chained log, scan every row and reject missing hashes, partial hash pairs, or gaps. Persist an explicit chain mode/start marker if historical unchained rows must be supported.

12. **Should-fix — [internal/kit/audit/redact.go:35](internal/kit/audit/redact.go:35) — Custom marshalers bypass audit redaction tags.** Structs implementing `json.Marshaler` or `encoding.TextMarshaler` are emitted whole without inspecting `audit:"redact"` or `audit:"-"` fields. This violates the redaction contract and can put secrets into the append-only log.  
    **Suggested fix:** inspect struct fields before honoring custom marshaling; reserve the scalar-marshaler shortcut for explicitly safe scalar wrapper types. Add a regression test with a custom-marshaled struct containing a redacted field.

13. **Should-fix — [db/migrations/mysql/20261022153800_kit_audit_log.sql:2](db/migrations/mysql/20261022153800_kit_audit_log.sql:2) — MySQL does not enforce or verify append-only audit privileges.** The table is created normally, and the runtime account can retain schema-wide `UPDATE` and `DELETE`. Hash verification is optional and cannot detect deletion of a valid chain tail.  
    **Suggested fix:** supply a MySQL privilege setup path that grants only `SELECT, INSERT` on this table, and make startup/doctor fail production readiness if the runtime account can update or delete audit rows.

14. **Should-fix — [internal/kit/users/service.go:55](internal/kit/users/service.go:55) — MySQL can report the wrong current version after an OCC conflict.** The initial unlocked `Get` establishes a Repeatable Read snapshot. If another transaction commits before the update, the update affects zero rows, but `occ.Check` reloads through the old snapshot and can return the obsolete version—or a row that has since been deleted.  
    **Suggested fix:** lock the row with `SELECT ... FOR UPDATE` before capturing `before`, compare the submitted version against that current row, and then update; alternatively make the OCC reload a locking/current read.

15. **Should-fix — [db/migrations/mysql/20261022153753_kit_users.sql:4](db/migrations/mysql/20261022153753_kit_users.sql:4), [internal/kit/users/store.go:37](internal/kit/users/store.go:37) — MySQL email identity semantics differ from PostgreSQL.** The MySQL column inherits the accent-insensitive `utf8mb4_0900_ai_ci` collation, and `ByEmail` uses `email = ?`. For example, an accented address can match an unaccented lookup, while PostgreSQL’s normalized comparison treats them separately.  
    **Suggested fix:** store the Go-normalized address under an explicit binary or accent-sensitive collation and use the same exact normalized comparison on both engines.

16. **Nit — [internal/kit/idempotency/middleware.go:85](internal/kit/idempotency/middleware.go:85) — A body exactly at the declared size limit is rejected.** Reading at most `MaxBodyBytes` and rejecting when `len == MaxBodyBytes` cannot distinguish an exact-size valid body from an oversized body.  
    **Suggested fix:** read at most `MaxBodyBytes+1` and reject only when the result is larger than the limit.

17. **Nit — [internal/kit/ratelimit/dbstore.go:59](internal/kit/ratelimit/dbstore.go:59) — Fixed-window reset time can be rounded down.** `Round(time.Second)` can advertise a retry one second before the actual window ends.  
    **Suggested fix:** use ceiling-to-seconds, as the memory store already does.

1. Dev login: fixed.
