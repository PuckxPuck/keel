# P6b review (Opus): the keel development tool

Scope: internal/app/modules.go; cmd/keel/{scaffold,make,make_gen,bench,upgrade,gen,steps,main}.go and their tests; cmd/keel/templates; the paging and ratelimit benchmarks; spec/; tools/go.mod; the CI bench job; Makefile; docs/cli.md and docs/conventions/modules.md. I did not review tenancy policy details, because P4 is changing them.

## Verdict: fix-then-ship

The generated module is a good teaching example. It uses a typed id, keyset paging over `paging.Sorts`, writes plus `audit.Record` in one `db.InTx`, a 409 on a stale version, a `Need` and a rate-limit class on every operation, a problem mapper and three lean tests. In throwaway copies it built, linted clean and passed its own tests on Postgres with tenancy, on Postgres without tenancy and on MySQL. One blocker remains: the committed OpenAPI documents describe an error shape the server does not send, and that shape changes when the first module is added. The should-fix items are mostly about generator safety.

## Blockers

1. **spec/*.openapi.yaml documents Huma's `ErrorModel`, not keel's `Problem`. The first `make:module` flips it, and oasdiff counts that as a breaking change.**
   - **Where.** internal/app/build.go:223-229 and internal/app/modules.go:44-54.
   - **Cause.** `Operations()` (used by `app openapi` and `route:list`) never calls `problem.Install`. Only `Build` does, at build.go:66-70. Huma therefore derives the documented error schema from its default `NewError`.
   - **What the documents say today.** All three documents describe `ErrorModel`/`ErrorDetail`, including a `value` property ("The value at the given location"). The server never sends `value`, and security.md forbids echoing it.
   - **What happens after a module.** `withModules` calls `problem.Install(m.Mapper)`, which replaces `huma.NewError` globally. The same export then switches to `Problem`/`FieldError`.
   - **Probe.** In a scratch copy I ran `make:module invoices`, then `oasdiff breaking --fail-on WARN` against the unmodified spec. Result: 34 errors on tenant and 2 on api (`response-property-type-changed`), exit 1.
   - **Impact.** Once a release is tagged with today's spec, any app's first module fails the compatibility check.
   - **Fix.**
     - Move the mapper installation into one function, called by both `Build` and `Operations()`, that also installs the module mappers.
     - Regenerate spec/.
     - Make `exportSpecs` (gen.go:137-145) fail when a document contains `#/components/schemas/ErrorModel`, so this cannot regress silently.

## Should-fix

2. **Partial failure leaves a half-made module, and a rerun refuses it.**
   - **Where.** scaffold.go:61-81, make_gen.go:186-198 and make_gen.go:231-237.
   - **Probe.** I changed modules.go so that `modules` returns a variable. `make:module orders` then wrote 9 Go files and 3 migrations before failing with "cannot find where to add the registration". A rerun failed with "internal/modules/orders already exists", and `tableIsNew` would refuse it too. `make:job` behaves the same way on a module that has no `Jobs` method.
   - **Fix.** Plan first, then write:
     - Render every file and compute every edit in memory.
     - Check that every target is absent.
     - Only then write.
     - Alternatively, on error remove `t.created` and restore the original bytes of `t.changed`.
     - Say in the error which line to add by hand.

3. **Name validation misses collisions that break the build or the migration.**
   - **Where.** make.go:27-45.
   - **Collisions with package-level names in internal/app.** `make:module codes` fails `go build` ("codes already declared through import", apikey_commands.go:179). `operations`, `realms`, `setup`, `serve` and `build` fail the same way.
   - **Collisions with the generated tests' imports.** `make:module strings` fails vet ("strings redeclared", module_test.go). `bytes`, `regexp`, `slices`, `httptest`, `assert`, `require`, `uuid` and `utf8` would fail the same way.
   - **SQL reserved words.** `make:module groups` writes a MySQL migration that fails with Error 1064. `rows` and `keys` would too.
   - **Fix.**
     - Derive the Go conflicts at generation time instead of keeping a list: parse internal/app's package-level identifiers, and parse the imports of the rendered templates.
     - Add a reserved-word list for both engines, or quote identifiers.
     - Apply the same checks to the table name in `make:migration ... create_<table>`.
     - docs/cli.md claims shadowing is refused; it is not, yet.

4. **The API compatibility check never runs in CI and silently skips without tags.**
   - **Where.** .github/workflows/ci.yml and steps.go:73-83.
   - **What is wrong.**
     - No workflow runs `checkAPICompat`. It only runs inside `keel check`, which CI does not call, although docs/cli.md says `check` is "everything CI runs".
     - `actions/checkout` defaults to fetch-depth 1 with no tags, so if it were added it would always print "skipped: no release tag yet".
     - That same message also covers "not a git repo" and "git missing". In this tree (`git init`, no commits) the skip is correct.
   - **Fix.**
     - Add a `keel compat` command and a PR step with `fetch-depth: 0` (or `fetch-tags: true`).
     - Use `git describe --tags --abbrev=0 --match 'v[0-9]*'` so deploy tags never count.
     - Report the git error when HEAD has no repository.
     - Compare the tag's file with the working tree's spec/api.openapi.yaml, which gen --check already keeps current, instead of a second `go run ./cmd/app`.

5. **`gen` fails for an app that dropped a dialect, whenever that engine is reachable.**
   - **Where.** gen.go:66-75 iterates the reachable engines, not `t.dialects()`.
   - **Probe.** With db/migrations/postgres removed and Postgres up: `gen postgres: migrations: no migrations found`.
   - **Impact.** Every MySQL-only app made by `keel init` hits this on a machine that runs both containers.
   - **Fix.** Skip engines that have no migration folder (and no internal/dbgen/<engine>).

6. **Template rot is not caught.**
   - **Where.** make_test.go:47-56 builds and vets only.
   - **What is missed.** The generated tests are never run, and the tenancy store test inlines `insert into tenants (id, slug, name, created_at, updated_at)` (store_test.go.tmpl:40). P4 is changing exactly that schema. I ran the generated tests by hand: they pass today, and nothing would notice the day they stop.
   - **Fix.**
     - Run `go test` on the generated package inside TestGenerators. It took 3-6 s here.
     - Replace the raw insert with a kit test helper owned by tenancy, for example `testdb.TenancyDB.NewTenant(t, slug)`.

7. **Nightly bench compares across different runner hardware.**
   - **Where.** ci.yml:111-131.
   - **What is wrong.**
     - The baseline comes from another night's VM. CPU models vary on ubuntu-latest, so a 10% threshold will flake, and n=6 cannot separate machine variance from a regression.
     - There is no documented way to accept a regression.
     - bench.go:80-85 writes the baseline even when the run found regressions. CI is safe because cache/save is skipped on failure, but locally `--save` silently accepts the regression.
   - **Fix.**
     - Cache the last-good commit SHA instead of results. Check it out in a worktree and run both on the same runner, then benchstat old against new.
     - Document how to accept a regression (a `workflow_dispatch` input, or `gh cache delete`).
     - Skip `--save` when regressions are found, unless `--force` is given.

8. **`MountJobs` is uncalled, and it builds a second wiring.**
   - **Where.** modules.go:80-89.
   - **What is wrong.** No queue is wired yet, so make:job registrations are inert. When P6 wires the queue, a second `newWiring` gives the job handlers different module instances (and a second audit recorder and sessions) from those serving HTTP. `Deps` also has no `*jobs.Queue`, so a service cannot "enqueue in the same transaction" as AGENTS rule 6 asks.
   - **Fix (P6).** Have Build return the module list (or its wiring), mount jobs from that, and add `Jobs *jobs.Queue` to the generated `Deps`.

## Generator design against tenancy policy

For create-table names, the generator writes a plain `create_<table>` file and then `<ts>_tenancy_<table>.sql` (module `tenancy`). This mirrors the kit and works today: the runtime tenancy schema check passed for `invoices`.

The P4 Opus review proposes refusing a Postgres `create table` without `tenant_id` or `keel:global` once tenancy is present. That check is per file, so it would refuse the generated create file.

For app modules, the split buys nothing. The app chose tenancy at `keel init`, and the split also hides the module's tenancy step from package test databases. Recommended: under tenancy, write `tenant_id`, tenant-leading keys, row-level security and the policy inline in the create migration. That is a change to the templates only. The rest of the generator (detection by internal/kit/tenancy, `db.Tx[db.Tenant]` in the store, the two-tenant store test) follows the policy without structural change.

## Nits

- **gen.go:134-145.** `gen` never deletes a spec file for a realm that no longer exists, so `gen --check` reports drift forever.
- **scaffold.go:176-179.** A hand-written single-line list `[]Module{a.New(...)}` gets a line inserted without a comma, which is a syntax error. `nameParam` (make_gen.go:74) assumes the parameter is named `w`.
- **store.go.tmpl:64-78 with service.go.tmpl:106-113.** `get(..., forUpdate=true)`, then a version compare, then `UPDATE ... WHERE version`, then `occ.Check`. Under the row lock the `occ.Check` callback cannot fire. Teach one path: the conditional update with `occ.Check`, with `before` read without a lock.
- **service.go.tmpl:97-127.** A PATCH carrying only `version` bumps the version and writes an audit row for no change.
- **service.go.tmpl:130 and handlers.go.tmpl:134.** Delete takes no version, so it can discard an edit made after the client read the record (rule 7). Consider a `version` query parameter that answers 409.
- **handlers.go.tmpl:40-42 and 50-51.** `format:"uuid"` means Huma answers 422 before `ParseID`, so the 404 branch is unreachable. 422 is also not in the declared errors for get and delete (module.go.tmpl:60,66).
- **module_test.go.tmpl.** Prints 13 request log lines per run. The app tests silence them with `logx.WithLogger(ctx, slog.New(slog.NewTextHandler(io.Discard, nil)))`.
- **Missing contextual rule.** modules.md step 6 asks for contextual `rbac.Can` checks, but the example has none. One small contextual rule would teach it.
- **docs/architecture.md:138.** Names an auth-resolve benchmark, which is absent.
- **bench.go:106-131.** Treats every unit as lower-is-better. A `b.SetBytes` benchmark (B/s) would invert this.
- **steps.go:79.** `tag:spec/api.openapi.yaml` is relative to the git root. Use `tag:./spec/...` so it works in a monorepo subdirectory.
- **make_gen.go:84-98.** `make:migration` does not check that the module exists.
- **Repository root.** It holds a stray 22 MB Mach-O `keel` binary (built 01:26) that is not in .gitignore.

- **Build and package tests.**
  - `go build ./...` is clean.
  - `go test -race ./cmd/keel` passes in 9.3 s; TestGenerators takes nearly all of it.
- **`go run ./cmd/keel check` in the real tree.** It fails at lint, on P4's in-flight `internal/kit/tenancy/tenancy_test.go:279` (`tenancy.Runner` arguments). That is not P6b. Because of this I could not get a green `check` on the real tree. The P6b parts were verified in copies.
- **Generators in scratchpad copies.** I ran `make:module invoices`, `make:job invoices send_reminder`, `make:command reports:rebuild`, `make:permission invoices.approve` and both `make:migration` forms.
  - Timestamps are real UTC.
  - Postgres and MySQL `gen` ran.
  - `keel lint` reported 0 issues.
  - The generated tests passed: rules, the store test under tenancy with the other-tenant probe, and the permission walk (403, then 403 with read only, then 503).
  - With tenancy hidden, the Postgres `db.Plain` variant passed. With Postgres skipped, the MySQL variant passed.
- **Generator safety probes.** Partial failure, name collisions (`codes`, `strings`, `groups`), refusing an existing module and an invalid name.
