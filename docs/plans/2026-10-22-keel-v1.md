# Plan: keel v1

Status: P0 to P6 done (2026-10-22 to 2026-10-23); P7 planned. Each phase below has a Done line and its reviews in [reviews/](reviews/). The rest of `docs/` describes what was built; `make init` became `keel init`.

## 1. What keel is

A Go backend template you copy to start a new service, or to port an existing one. It ships the parts every service rebuilds (configuration, HTTP and OpenAPI, errors, sessions and sign-in, permissions, optional multi-tenancy, audit, rate limits, database access and migrations, background jobs, mail, files, imports and exports, tests, deploy) and nothing about any one product. No UI: an app adds its own web client, mobile app, or none.

It is a template, not a library. `make init` makes a new repo from it; from then on the code belongs to that app. To keep later upgrades cheap, everything under `internal/kit/` is written app-agnostic and is never edited for one app's needs, so a kit fix can be copied from keel into any app as a plain diff (see [../operations.md](../operations.md#upgrading-kit-code)).

## 2. Goals and non-goals

Goals
- A new service is answering authenticated, permission-checked, rate-limited, audited requests against a migrated database on day one, with tests and CI green.
- Postgres or MySQL, chosen once per app at `make init`. Kit code and its SQL exist for both and are tested on both. Multi-tenancy needs Postgres.
- Multi-tenant SaaS is a first-class shape: tenants, users in several tenants with a role in each, row-level security, and a separate operator realm for the people who run the service.
- Porting an existing app (Laravel or another Go service) is a mapping exercise with a guide, not a design exercise ([../porting.md](../porting.md)).
- Secure by default: production refuses to start with unsafe settings ([../security.md](../security.md)).
- Readable by agents: one entry file (`AGENTS.md`), conventions written down, every rule backed by a test.

Non-goals
- UI, design system, or frontend tooling.
- Runtime switching between databases. One app runs one engine.
- Database-per-tenant or schema-per-tenant. Tenancy is shared tables with row-level security.
- Multi-region, sharding, or event sourcing. The target is a modular monolith on one to a few instances.
- A plugin system. Optional parts are removed at `make init`, not toggled at runtime.

## 5. Phases

Each phase ends with `make check` green on both databases (tenancy phases on Postgres), a review (Opus reviewer, plus the Codex reviewer for P2 to P5, blind to each other), and an update to `docs/` if behaviour moved. Implementation runs on the coder agent: Sonnet for P0, P1, P6 and P7; Opus for P2 to P5 (data, auth, tenancy, concurrency).

### P0. Skeleton and tooling
- `go.mod` (Go 1.27), tool directives for the Jet generator, golangci-lint, govulncheck, goose, oasdiff.
- Makefile targets are thin wrappers over `keel` (`make check` runs `keel check`), so CI, humans and agents run the same thing.
- `kit/cli` and the empty `app` and `keel` binaries with `list` and `--help`.
- `.golangci.yml` (v2): standard set plus errorlint, gosec, revive, bodyclose, noctx, contextcheck, rowserrcheck, sqlclosecheck, nilerr, errname, exhaustive, gocritic, intrange, testifylint, fatcontext, usestdlibvars; gofumpt and goimports formatters; depguard forbids `unsafe`; nilaway as an advisory step; `CGO_ENABLED=0` everywhere.
- `docker-compose.yml`: every port bound to 127.0.0.1, images pinned by version, profiles `pg`, `mysql`, `mail`, `pdf`, `s3`. The Postgres init script creates the three database roles (owner, app, operator) so local runs match production.
- CI: on PRs, lint, vuln and tests on one engine in parallel jobs, under 10 minutes; the full matrix (Postgres 17 and 18, plus 19 once released; MySQL 8.4 and 9.7), fuzzing and benchmarks on main and nightly; spec and generated-code drift using `git status --porcelain` so new untracked generated files fail too, and `oasdiff breaking` against the last release tag.
- Done when: `make check` runs green on an empty module.

**Done.** Module, tools, lint config, compose, CI and the `keel` and `app` skeletons. Reviews: [2026-10-22-p0-p1a](reviews/2026-10-22-p0-p1a.md).

### P1. Foundation
- `config`: parts embedded by the app config, env prefix, `_FILE` secrets, `config.Secret` redaction, `Validate(prod)` per part joined with `errors.Join`.
- `logx`: JSON `slog`, a context handler adding request id, trace id, user id, tenant id and client IP to every record.
- `clock` (`Wall` and `Business`; `Today` takes the location), `ids` (UUIDv7, v5), `buildinfo`.
- `httpx`: router, Huma setup with explicit `problem.Install`, problem+json with extension members and error mappers, request id, recover (re-panics `http.ErrAbortHandler`, never writes after headers went out), access log with the route pattern, client IP resolution (trusted proxies, Cloudflare proxy and tunnel modes), security headers, CSRF via `http.CrossOriginProtection`, optional CORS allowlist, body and header limits, docs and spec routes off in production.
- `httpx` envelope types `One[T]`, `List[T]`, `Feed[T]`, `NoContent`; not-found, method-not-allowed and recover all answer problem+json; the operation walk test checks every output schema.
- `ids.ID[T]` typed ids with JSON, SQL and Jet conversions.
- `health`: `/livez`, `/readyz`, startup gate. Server lifecycle with `errgroup`, all four `http.Server` timeouts, readiness flip, drain delay, ordered shutdown.
- `money`: `money.Amount{Minor int64, Currency string}` with exponents from `bojanz/currency`, checked add and subtract, allocation without losing a minor unit, rounding from `decimal` with a named mode; JSON shape `{"amount": 1250, "currency": "USD"}`.
- Done when: table tests for client IP, recover, problem mapping, config profiles, money allocation and rounding; fuzz tests for cursors and ids; one benchmark for the envelope encoder (run by `keel bench`, not by `go test`).

**Done.** config, logx, clock, ids, buildinfo, money, dates, httpx with problem+json and client IP, health and server. Reviews: [2026-10-22-p0-p1a](reviews/2026-10-22-p0-p1a.md), [2026-10-22-p1b](reviews/2026-10-22-p1b.md).

### P2. Database
- `db`: open for both drivers with pool tuning, session settings, TLS policy. Named pools (`app`, `operator`) from separate URLs so the operator pool can use a role that bypasses row-level security.
- `db.InTx` with panic rollback, rollback on a detached context, bounded retry on serialization failure and deadlock, read-only and isolation options, `AfterCommit` hooks, `ErrCommitUncertain`, and a `Begin` hook (tenancy uses it to set the tenant at the start of every transaction).
- Dialect-neutral error helpers; `db.Lock(ctx, tx, name)` over the `locks` table.
- `migrate`: goose provider over embedded SQL, session locker, runs as the owner role, `up | down | status | validate | version`, `down` and `reset` refused in production, startup schema check.
- `testdb`: one database per test package (Postgres template clone; MySQL table copy), seeded templates, a janitor; tests connect as the app role, never the owner.
- Spike first (half a day): Jet on `database/sql` with pgx stdlib (uuid, `jsonb`, arrays, `xid8`, nested-struct scans, `FOR UPDATE SKIP LOCKED`) and on MySQL with `char(36)` ids; `db.Insertable`, `paging.Keyset` rendering for both dialects; `make gen` from a scratch database. Exit plan in decisions.md D4.
- Done when: the tx, retry, lock and migrate tests pass on both engines.

**Done.** db with typed transactions, migrate with the contract lint, testdb, paging, Jet types through `keel gen`. Reviews: [2026-10-22-p2-opus](reviews/2026-10-22-p2-opus.md), [2026-10-22-p2-codex](reviews/2026-10-22-p2-codex.md).

### P3. Identity and access
- `httpx` host routing for realms (moved from P1): requests are dispatched to a realm by host.
- `auth`: sessions with realms (D17). Each realm has a name, hosts, cookie name, idle and absolute expiry, MFA policy, principal loader and permission catalogue. Token is 32 random bytes stored as SHA-256; `__Host-` cookie in production; rotation on sign-in, MFA step-up and privilege change; revoke all for a user; `Resolve` and `Require` split; principal cache with a short TTL. Bearer tokens (API and device kinds) from the same table, never from a cookie or query string; device tokens rotate with a grace window.
- `auth/password`: argon2id with configured parameters (D20), bounds on verify, `NeedsRehash`, a semaphore on concurrent hashes, legacy bcrypt verify and rehash, delay-based throttling by account and IP (never a remote lockout).
- `auth/tokens`: single-use tokens for password reset, email verification and invites: 32 random bytes, SHA-256 stored, purpose-bound, 60-minute default expiry, consumed in the same transaction as the change; a reset revokes the user's other sessions.
- `auth/totp`: TOTP (RFC 6238) enrolment with confirmation, last used step stored to stop replay, ten single-use recovery codes stored hashed, secrets encrypted at rest with a key from config.
- `auth/passkey` (optional): WebAuthn registration and sign-in through go-webauthn (pre-1.0; pinned, upgrades reviewed), challenge state server-side and single use.
- `auth/oidc` (optional): PKCE S256, `state` and `nonce` server-side and single use, ID token checks.
- `auth/devlogin`: local only, loopback only, 404 when off.
- `rbac`: catalogue per realm, roles and role permissions as data, optional scoped grants, `Need` enforced by middleware (fail closed), guardrails as pure functions with a policy.
- `audit`: `Record(ctx, tx, Event)` requires a transaction, enriches actor, realm, tenant, on-behalf-of, IP and request id from context, redacts secret fields, optional hash chain.
- `ratelimit`: `DBStore` for security counters (D31), class registry, token buckets, keys by address, network, principal, tenant or hashed token; bounded memory; `RateLimit` and `Retry-After` headers; startup check that every operation has a class.
- `apikeys` (optional): key format with checksum, SHA-256 storage, scopes from API-grantable permissions with the grant guardrail, `api` realm with bearer auth and its own OpenAPI document, `api.Public(since)` marking, per-key and per-tenant rate limits, expiry reminders, revocation on the next request (the row is read every request, D34).
- `webhook` (Standard Webhooks verify and sign), `occ`, `idempotency` (`Idempotency-Key` for short retry windows; long-lived offline replay is a module pattern, see conventions/api.md).
- Done when: permission walk, session expiry, rotation and realm isolation, guardrails, password bounds, token single use, TOTP replay, API key scope and revocation, and webhook vectors pass; fuzz tests for API keys and webhook signatures.

**Done** in three steps: realms, rbac, users, audit, rate limits, occ, idempotency and inbound webhooks (P3a); sessions, password, tokens, TOTP, devices and dev login (P3b); oauthstate, OIDC, passkeys and API keys (P3c). Reviews: [2026-10-22-p3a-opus](reviews/2026-10-22-p3a-opus.md), [2026-10-22-p3a-codex](reviews/2026-10-22-p3a-codex.md), [2026-10-22-p3b-opus](reviews/2026-10-22-p3b-opus.md), [2026-10-22-p3b-codex](reviews/2026-10-22-p3b-codex.md), [2026-10-22-p3c-opus](reviews/2026-10-22-p3c-opus.md), [2026-10-22-p3c-codex](reviews/2026-10-22-p3c-codex.md).

### P4. Tenancy (optional, Postgres only)
- Tables: `tenants` (id, slug, name, status), `tenant_domains`, `memberships` (user, tenant, status, default flag); `user_roles` gains `tenant_id`; roles are per tenant, created from built-in templates when a tenant is created.
- Resolution: from the request host (subdomain or a custom domain in `tenant_domains`) or the session's current tenant. The user must hold an active membership, else 403. Switching tenant rotates the session and drops the principal cache.
- `db.Tx[db.Tenant]` and `db.Tx[db.Operator]` (D29); the tenant-setting lint and pre-commit re-read (D30).
- `tenancy.Middleware` puts the tenant in the context; `db.InTx` on the app pool runs `select set_config('app.tenant_id', $1, true)` first in every transaction. No session-level `SET`.
- Row-level security on every tenant table: `enable` and `force`, one policy `using (tenant_id = (select nullif(current_setting('app.tenant_id', true), '')::uuid))` with the same `with check`. An unset tenant sees nothing.
- Database roles: owner (migrations, owns objects), app (`nobypassrls`, not owner), operator (`bypassrls`, used only by the operator realm's pool). Cross-tenant work happens on the operator pool, never by loosening a policy.
- Tenant-aware kit parts: jobs store `tenant_id` and run in a tenant transaction; cross-tenant sweeps enumerate tenants on the operator pool and fan out one job per tenant; file keys start with the tenant id; audit rows carry `tenant_id`; rate limits can key by tenant.
- Tenant access state: `active`, `read_only` (unsafe methods refused with 403 `tenant_read_only`, except operations marked `tenancy.AllowWhileReadOnly`, such as billing), `suspended` (requests refused, that tenant's sessions cleared). The state comes from the app (for example a billing module) through a `tenancy.StateSource`.
- Migration lint and a catalogue test: any table with a `tenant_id` column must have RLS enabled and forced, a policy, `tenant_id` leading its indexes, and composite unique and foreign keys that include `tenant_id`.
- CLI: `app tenant create|list|suspend|resume`.
- Done when: tenant A cannot read or write tenant B through any operation (a walk test with two tenants), an unset tenant returns zero rows, jobs restore the tenant, the catalogue test fails on a table missing RLS, and the operator pool reads across tenants.

**Done.** kit/tenancy, tenant migrations for every kit table, the operator pool and realm, the D30 lint, tenant-aware kit parts. Reviews: [2026-10-23-p4-opus](reviews/2026-10-23-p4-opus.md), [2026-10-23-p4-adversarial](reviews/2026-10-23-p4-adversarial.md), [2026-10-23-tenancy-codex](reviews/2026-10-23-tenancy-codex.md).

### P5. Async and IO
- `jobs`: enqueue in the caller's transaction, unique key, priority, lanes, `for update skip locked`, wall-clock lease with renewal and handler cancellation when the lease is lost, shutdown requeue without spending an attempt, jittered backoff, permanent errors, cron schedules with a location, retention job, partial index on open jobs, metrics hooks, tenant carried and restored.
- `mail` (optional): `Mailer` (SMTP via go-mail, log, recorder), outbox log with `sending` written before contact, stable Message-ID, app-supplied layout, payload redaction after send, templates for the reset, verify and invite flows.
- `files` (optional): `Storage` (local through `os.Root`, S3), streamed uploads with a cap, sha256, fsync and rename, pending row then object, staged and attached by the uploader, delete after commit, sweep, `files/inspect`, optional AV hook, `fileshttp` adapter, public and private visibility (public objects served through signed, expiring URLs or a CDN path, never guessable keys).
- `webhooks` (optional, outbound): tenant endpoints, `Emit` in the causing transaction, delivery jobs with backoff, auto-disable, replay, SSRF-safe dialer.
- `connections` (optional): provider interface, OAuth 2.0 with PKCE, encrypted tokens, refresh under a lock, revoke on disconnect.
- `xlsx` (optional): excelize behind a small reader and writer. The reader caps file size, sheets, rows and cells and streams rows; the writer streams and neutralises formulas like `csvx`.
- `barcode` (optional): QR, Code 128 and EAN-13 to PNG or SVG through boombuler/barcode.
- `pdf` (optional): Gotenberg client with a size cap, `%PDF-` check, basic auth, assets sent with every request.
- `csvx`, `docx` (optional), `dates`.
- `paging`: keyset cursors bound to sort and filters, one query per sort with a matching index, capped offset and capped totals, and change feeds with tombstones (commit-safe on Postgres through `xid8` and the snapshot xmin; lag window on MySQL).
- Done when: SSRF dialer tests (private, loopback, link-local, metadata, DNS rebinding), concurrent refresh test, job lease, crash and tenant tests, mail rerun tests, the storage contract, inspect corpus, xlsx limits, the keyset walk under concurrent writes, and the late-commit feed test pass.

**Done.** jobs, mail, outbound webhooks, connections and seal (P5a); files with inspect and fileshttp, xlsx, barcode, pdf, csvx, docx and change feeds (P5b). ## 6. Risks and open questions

| Risk | Mitigation |
| --- | --- |
| Jet on `database/sql` misses a type or construct we rely on | P2 spike before anything else; the store escape hatch covers rare queries; exit plan in D4. |
| A tenant table ships without RLS | Catalogue test and migration lint fail the build; tests run as the app role, which cannot bypass. |
| Operator pool used from tenant code | The operator pool is only in the operator realm's `Deps`; a lint forbids it in tenant modules. |
| Two dialects double kit SQL and tests | Kit SQL is small and frozen early; CI runs both. Apps carry one. Tenancy is Postgres only. |
| MySQL DDL is not transactional | One statement per migration file on MySQL, enforced by `migrate validate`. |
| go-webauthn is pre-1.0 | Optional part, pinned, upgrades reviewed against its changelog; challenge data never kept across releases. |
| Template drift between apps | Kit code is never edited per app; upgrades are diffs; `docs/operations.md` has the procedure. |
